执行摘要

结论: GLM-5.3-Flash 全量模型在昇腾 NPU 上的 SFT 训练已完整跑通。 20/20 训练步(iteration)全部完成, 损失(loss)从 9.77 收敛至 0.083(117 倍), 全程零崩溃、零 NaN。

本次任务的核心价值在于解决了一个困扰 14+ 轮实验的关键问题:

  • **根因**: 小 batch 数据形态下 MoE 专家并行的 alltoallv 通信会出现"零数据量传输"(0-size), 而昇腾通信库(HCCL)对该特殊路径存在缺陷, 导致发送端与接收端的通知(notify)握手永不完成, 全体 64 卡同步冻结, 约 20 分钟后被设备看门狗终止。该结论经最小化实验独立复现(正常场景 1 秒完成, 零传输场景挂起 5.5 分钟后崩溃), 非推断。
  • **解法**: 将训练序列长度从 64 放大到 1024, 使每个通信域 rank 平均接收的 token 数从 2 提升到 32, 零传输概率从工程上可见(约 7.4e-4/次调用)降至可忽略(约 1e-14/次调用)。解法仅改数据形态参数, 零内核改动, 与社区 DeepSeek V4 的工程实践同源。
  • **结果**: 训练 20/20 步完成, loss 9.77→0.083; 稳态每步 89.4 秒, 吞吐 366 tokens/s(64 卡), 显存峰值约 54GB/卡(84%)。

遗留事项(详见第 5 章): 全量规模的数值一致性对拍(pearson ≥ 0.995)与 GSM8K 效果对比评估待执行, 均已给出成本估算与执行计划。

第 1 章 项目背景与目标

1.1 任务背景

1.1.1 训练对象：GLM-5.3-Flash

GLM-5.3-Flash 是 GLM 5.3 系列的稀疏 MoE 大语言模型，也是本次 SFT（监督微调）全量训练任务的对象。它的规模与结构特征如下：

维度数值说明
总参数量321.32B权重实测口径（safetensors 全量分片遍历）：专家 311.65B + dense 7.84B + vision/misc 1.83B；绝大部分参数位于 288 个专家中
层数45 层流水线并行（PP2）下按 22+23 非均匀切分
专家数288MoE 稀疏路由，专家并行（EP32）切分到 32 个通信域 rank
权重体积643GB（BF16）HF 原始格式真权重，需分布式加载
注意力机制fla KDA（delta attention）线性注意力变体，经 triton-ascend 移植的昇腾算子核

选择这个模型做全量训练验证，是因为它同时压中了训练链路上三个最难的点：

1. 规模之难：321.32B 参数、643GB 权重，单卡显存（64GB）连权重的十分之一都容不下。必须做 TP（张量并行）× EP（专家并行）× PP（流水线并行）× SP（序列并行）四维联合切分，且每维切分都有严格的整除与布局约束——这是 HBM 预算层面的硬约束。

2. 结构之难：fla KDA（delta attention）是尚未在昇腾生态中充分验证的新算子族，且与 MoE 稀疏路由叠加——注意力侧和专家侧各有一条全新的算子与通信路径，二者在反向传播中还会交叉耦合。

3. 生态之难：昇腾 NPU 不是 CUDA 生态。训练引擎（MindSpeed-LLM）、权重桥接（mbridge）、注意力算子（fla 0.6.0 + triton-ascend）、通信库（HCCL）全部需要逐层适配验证，没有任何一条"官方直跑"路径可以依赖。

1.1.2 任务意义

在昇腾 NPU 上跑通 GLM-5.3-Flash 全量 SFT 训练，具有三层意义：

  • **国产算力栈的关键里程碑**：昇腾 910B + CANN 生态此前已在中等规模模型上验证了训练能力，但在 300B+ 级 MoE + 新型注意力组合上的全量训练尚未打通。本次任务是该组合在国产算力栈上的完整链路验证——证明昇腾集群不仅能推理、能跑小模型，也能承担头部大模型的训练负载。
  • **全量强化学习（RL）的前置条件**：后续的 GRPO 全量强化学习训练以 SFT 权重为起点、以 SFT 训练链路为基座。SFT 全量链路不通，RL 无从谈起；反之 SFT 链路的每一次修正确认，都会整体复用到 RL 部署上。
  • **与社区路径形成对照**：同栈的 DeepSeek V4 训练已稳定运行数百步，说明昇腾训练栈本身是可信的。GLM-5.3-Flash 与之的差异（fla 注意力、288 专家、小 batch 数据形态）正是需要本地验证的变量面。

1.1.3 前置工作与本次任务定位

本次全量训练并非从零开始，而是建立在两条已收口的前置链路上：

第 3 章 核心问题与根因分析

本章是全报告的技术核心：一场持续 14+ 轮部署的历史性卡死，最终被定位为一个"单字节都不传输"的通信边界缺陷，并通过最小化 Demo 拿到决定性证据。

3.1 现象：一场持续 14+ 轮的"训练不结束"

3.1.1 时间线

全量训练的第一阶段（8 节点 64 NPU 原生 pretrain 入口）自启动之日起，就陷入"启动—卡死—重启"的循环，历时约一周：

09-03  全量 SP 训练门禁部署启动（8 节点 64 NPU，HF 真权重）
  │
09-04  首个死锁定位：iteration 2 反向集体通信死锁
  │
09-05  对照排查多轮推进（每次单变量改动，同点再崩）：
  │     → "0-size 输出缓冲 NULL 指针"定案并修复 → 修复后仍崩
  │     → 集群端口冲突独立根因修复 → 仍崩
  │     → 反向 0-size 死锁机制定位 → 修复后仍崩
  │     → 计数探针排除"集体通信调用序分歧"假设
  │
09-06  全量 RL 部署链推进 12+ 轮修复，仍复现同类卡死签名（签名逐点一致）
  │
09-07  用户裁决：全量直上分支暂停，重塑为消融阶梯
  │     msprof 全节点采样点名 alltoallv → 最小化 Demo 独立复现定案
  │     → 数据形态修复（SEQ 放大）→ 验证轮 20 iters 全量跑通 ✅
  │
09-08  全量 SFT 训练报告
注：09-06 的 RL 链与 SFT 链（本报告主题）共享数据形态与通信栈，卡死签名逐点一致——这是根因跨形态普适的佐证；09-07 裁决全量直上分支暂停后，04 全量 SFT 作为消融阶梯首步推进。

3.1.2 故障指纹：一个高度一致的"卡死签名家族"

多轮卡死表面上报错位置随机漂移，但底层签名高度一致——这是后期判别的重要抓手：

指纹观测内容
全体 rank 卡在 backward进程全景采样显示全部 64 rank 同步卡在 autograd 反向（流水线 backward_step）
集体通信排队超时各 rank 的 ALLTOALL（MoE 专家通信）/ ALLGATHER 相继报 dispatch timeout
固定延迟看门狗从首个超时到进程崩溃存在固定延迟（同一看门狗家族，逐轮 ±1s 复现）
507034 / 507018 / 507048通信停滞报错 / 20 分钟看门狗 SIGABRT / "stuck notify" 挂起家族错误码
报错 rank 漂移、停滞源固定哪个 rank 先报错取决于看门狗先超时，具有随机性

最令人困惑的一点：每轮修复（端口、指针、探针、并行参数）后，卡死依然在同一位置复现，且签名逐点一致——仿佛有一个"看不见的根因"在所有显性修复之外。

3.2 排除过程：三条假设逐一证伪

按照"先建模、再行动"的排查纪律，多轮排查聚焦三条候选根因，逐一验证排除：

#候选假设验证方法验证结果结论
①fla 注意力核挂起（计算核死循环）单卡重放 SFT 真实 shape（B=1/S=64/D=128），5 个随机种子，真权重 layer0 切片前向 6.9s（含首次编译）+ 反向 0.24s 正常完成；**5 条梯度（q/k/v/g/beta）全部 FINITE**排除
②0-size 输出缓冲 NULL 指针（AICPU 0x2a）mcore 补丁（输出缓冲保有效指针）部署并验证运行期生效补丁生效日志确认出现，卡死依旧、签名逐点一致排除（指针面）
③reshape / 衔接布局错误PP 边界 flatten/unflatten、o_norm 输出衔接等契约形状逐一静态对账全部形状匹配，无布局分歧排除

三条排除各有意义：

  • **假设①（fla 核挂起）**是嫌疑最大的对象——fla 核是自研移植核，且在设备侧观测到过"AICore 100%"的忙状态，历史上曾被认为"计算核自旋"。但单卡重放给出了干净的否定：在 SFT 的真实训练 shape 下，fla 核前向反向均正常完成、梯度全有限。这同时澄清了一个被长期混淆的事实：fla 核确实存在编译失败（UB 溢出），但那是强化学习长序列 shape 专属问题，与 SFT 短序列卡死无关——两个问题被错误地捆绑判读过。
  • **假设②（0-size 输出缓冲）**排除过程最微妙：早期曾将卡死定案为"AICPU alltoallv kernel 参数非法（0x2a）"，根因是 0-size 输出缓冲的 data_ptr 可能为 NULL。补丁将缓冲分配改为"至少 1 元素后再切回 0 元素"——语义零变化，仅保证指针有效。补丁运行期确认生效，但卡死依旧。**这个结果并没有宣告 0-size 无罪，而是把嫌疑从"指针非法"精确迁移到"0-size 传输本身"**——后者正是最终根因。需要说明排除口径：该"排除"是针对**指针面**的排除——补丁保留 0-size 传输、仅保有效指针，崩溃依旧，恰好说明嫌疑在传输本身；指针面排除 ≠ 传输面排除，传输面由 3.3 的 msprof 采样与 3.4 的 Demo 最终定案。
  • **假设③（reshape 衔接）**是卫生性排除：确认流水线边界与注意力输出衔接的布局契约全部匹配，把排查面收拢到通信层。

3.3 根因定位：msprof 全节点采样点名 alltoallv

三条假设排除后，排查面收敛到通信层。此前 msprof 环形采样尝试曾因参数错误失败、从未产出有效采样；本次改用部署脚本的 task-based 全节点配置（64 NPU 全开）成功捕获卡死窗口。决定性的观测来自 msprof 全节点采样：在 64 块 NPU 上同时开启设备侧 profile（task-based 模式，AI Core / 运行时 API / AICPU / HCCL 全开），完整记录卡死窗口内每个 rank 的算子级执行轨迹。

采样结论：

全体 rank（64/64）冻结在同一个位置：
  MoE 专家路由的 alltoallv 通信上
  —— 接收端处于 Notify_Wait（等待发送端通知）状态，且永不满足

也就是说：没有任何一个 rank 在"算"，全体 rank 都在"等"。alltoallv 是 MoE 稀疏路由的核心通信原语——token 按专家归属在 32 个 EP rank 之间交换。它不完成，则该 rank 后续所有集体通信排队，进而整个集群互等。

这一结论与 3.2 的单卡验证完全咬合：单卡 dbeta 等 5 条梯度全部 FINITE 证明 fla 数值链无罪，msprof 则证明设备级冻结发生在通信而非计算——"计算核卡死"的历史判读是误判，真相是通信挂起。回看此前"AICore 100%"的观测，也与最终机制自洽：发送端在快速失败的重试循环中保持忙（AICore 100%），接收端在 Notify_Wait 上静止等待（AICore 0%）——两种状态并存，恰是 0-size 握手缺陷的一体两面，而非计算死循环。

3.4 决定性证据：最小化 Demo 独立复现

msprof 给出了"冻结在 alltoallv"的强证据，但训练栈内证据链再长，也难免与历史误判一样被质疑。因此设计了栈外最小化 Demo：剥离全部训练逻辑，只用 2 节点 4 rank 的最小通信环境，单变量对照"0-size 是否触发挂起"：

场景构造结果
场景 A（对照组）各 rank 传输非零 token 数**1 秒完成**，通信正常
场景 B（实验组）注入一个 rank 零接收（0-size alltoallv）**挂起 5.5 分钟**后崩溃，报错 507048（"0 stuck notify wait"）

这是本次战役的决定性证据：

1. 单变量：与生产环境的唯一差异就是 0-size，其他全部相同；

2. 最小环境：2 节点 4 rank，排除了节点数量、模型结构、算子栈等一切混淆因素；

3. 可复现：场景 B 必挂起，不是概率事件；

4. 与生产同族：错误码 507048（stuck notify）与生产现场 507018/507034（20 分钟看门狗 SIGABRT、通信停滞）同属 notify 握手挂起家族。

至此根因闭环：0-size alltoallv 在昇腾 NPU 的 HCCL 上必然挂起——这是通信库对"零字节传输"的边界缺陷，与模型代码、算子实现、并行参数均无关。需要澄清排除口径：早期指针卫生修复只覆盖指针面（保证 data_ptr 非 NULL），未触及传输面（notify 握手）；"指针面修复后仍挂起"并不构成对 0-size 假设的证伪——指针面排除 ≠ 传输面排除。传输面由本节的干净单变量 Demo（场景 A 1s 正常 vs 场景 B 注入 0-size 挂起 5.5 分钟、报错 507048）与验证轮 20/20 iters 完整跑通最终定案。

3.5 机制详解：0-size 传输的 notify 握手缺陷

3.5.1 握手机制

HCCL 的 alltoallv 传输依赖发送端与接收端之间的 notify 握手完成同步。正常路径与 0-size 路径的差异如下：

【正常传输（非零字节）】
发送端 rank i                        接收端 rank j
   │                                    │
   │──── Notify_Record（注册传输）───►   │
   │                                    │ 收到通知, 开始接收
   │──── 数据字节流 ─────────────────►   │
   │◄─── Notify_Done（完成确认）────    │
   │                                    │
   握手闭合, 传输完成 ✅

【0-size 传输（缺陷路径）】
发送端 rank i                        接收端 rank j
   │                                    │
   │──── Notify_Record（0 字节）─────►  │
   │◄── 快速失败（record 不成功）──     │ 进入 Notify_Wait: 等发送端通知
   │                                    │
   │──── 重试 Notify_Record ─────────►  │
   │◄── 再次快速失败 ─────────────────  │
   │  (反复重试, 每次快速失败 = 自旋)    │  等待永不满足 = 永久等待
   │                                    │
   └── 发送端: AICore 忙(100%) ──┐     │
                                 └── 接收端: AICore 闲(0%) ──┘

通俗地说：发件人反复敲一家已经打烊的店门（每次快速失败、立刻重试），收件人在店里等一件永远不会送达的包裹。双方各自卡在自己的一侧，没有任何一方能主动打破这个僵局。

3.5.2 死锁传播：从一对 rank 到全集群

单个 0-size 卡住的是一对 rank 的握手，为什么会冻结全体 64 rank？答案是 EP 环上的集体依赖：

EP32 通信环：rank0 → rank1 → ... → rank31 → rank0（循环依赖）

  某 rank 在某 MoE 层 alltoallv 上握手断裂（0-size）
  → 该 rank 的 MoE 前向不完成
  → 其后续集体通信（下一个 ALLTOALL / ALLGATHER）排队, 派发停滞
  → 对端 rank 在其各自的后续集体通信上等待它
  → 环形等待扩散 → 全体 rank 互等 → 全集群冻结
  → 20 分钟看门狗到期 → SIGABRT（507018, 首个触发 rank 崩溃, 其余随后）

流水线反向（backward）阶段尤其致命：反向的 token 反路由 alltoallv 会把"前向零接收"翻转为"反向零发送"——0-size 在反向路径再次出现，且此时所有 rank 已进入反向集体通信的互相等待，死锁一发不可收拾。

3.5.3 为什么我们必触发，而社区路径天然规避

0-size 是否出现，取决于一个简单的统计事实：token 越少、专家越分散，零接收概率越高。

数据形态                每 EP rank 平均 token  零接收概率（泊松近似，均匀假设）
─────────────────────────────────────────────────────────────
MBS=1 × SEQ=64   →    64 / 32 = 2 token/rank  →  e^-2 ≈ 13.5%（必现级）
MBS=1 × SEQ=1024 →  1024 / 32 = 32 token/rank →  e^-32 ≈ 1.3e-14（可忽略）
DeepSeek V4 大 batch → 数千 token/rank        →  ≈ 0（天然规避）
  • **我们（修复前）**：MBS=1、SEQ=64 的极小 token 形态——每层全局 64 token，经 32 个 EP rank 均分后每 rank 平均仅 2 个 token——零接收从"理论可能"变成"实测必现"。实测锚点（2026-09-05 探针轮）：5360+ 次 alltoallv 调用中记录到 4 次零接收事件（≈7.4e-4/调用）。该实测率低于均匀泊松假设的 e^-2≈13.5%（约两个数量级）——路由的负载均衡使真实分布比均匀随机模型更均匀；但即便按实测率，每 iter（约 2,880 次调用）仍期望出现约 2 次零接收，且真实路由偏斜/负载不均使事件率偏离均匀假设——这正是生产环境必现的原因。
  • **社区对照（DeepSeek V4）**：同栈 467 步训练零事故。其数据形态为大 batch（每 rank 数千 token），零接收概率约等于零——这反过来说明 0-size 挂起是**极小 token 数下的边界条件触发，而非昇腾通信栈的普遍缺陷**。
  • **Mini 规模对照**：减层门禁（EP2）为什么 20 iters 顺利通过？因为 2 个 rank 交换 256 槽位，平均每 rank 128 槽位——0-size 在概率上不可能发生（e^-128 量级）。

运行窗口累积概率（让"数学上不可能"可量化）：每 iter 约 2,880 次 alltoallv 调用（45 层 × 32 rank × 前向/反向），20 iters 共约 57,600 次，期望零接收事件 ≈ 57,600 × 1.3e-14 ≈ 7×10^-10——远小于任何工程风险阈值（1000 iters 长训 ≈ 4×10^-8，同样可忽略）。

3.6 解法与验证

根因定案后，解法沿"消除 0-size 触发面"展开，历经两轮：

方案思路结果
clamp 钳位（尝试后废弃）把零项钳为 1，用 dummy token 贯通①补丁对称性缺陷导致新崩溃（0x2a 变体）；②补丁多次叠加后状态混乱（同一块代码 4 处重复钳位），其间"无 0-size 仍死锁"的观察发生在补丁叠加污染的容器上、且只覆盖指针面，效力存疑，不构成对根因的证伪——不稳定，废弃

SEQ 放大方案与 DeepSeek V4 社区路径同款——不修通信库，而是从数据形态上让 0-size 不可能发生。代价可控：HBM 升至 ~54GB/卡（84%）、短样本 padding 计算开销（详见第 5/6 章）；收益 = 从概率根上消除 0-size 触发面（彻底绕开一个无法从应用侧修复的通信库边界缺陷）。

3.7 为什么拖了 14 轮（结构性复盘）

14+ 轮部署仍未收敛，是本次战役最容易被追问的数字。复盘下来，周期之长并非根因本身有多隐蔽，而是四个结构性因素叠加：

1. 指针面修复不完整，被误读为"修复无效"：早期定位到"AICPU 0x2a 指针非法"并部署指针卫生修复（仅保证输出缓冲 data_ptr 有效）。补丁确认生效但卡死依旧——正确的解读是"修复只覆盖了指针面、未触及传输面"，但当时一度被误读为"修复方向错了"，排查注意力被引离 0-size 本身。

2. 指针面与传输面混淆，形成一次误排除：在一次判别轮中，"指针修复后仍崩溃"被解读为"0-size 排除为根因"，排查方向一度转向 fla 计算核。事后看，指针面的排除并不等于传输面的排除——补丁保留 0-size 传输、仅保有效指针，崩溃依旧恰好说明嫌疑在传输本身（见 3.2 排除②）。

3. 观测工具不足，把排队表象当卡点：卡死窗口早期只有进程级采样，看到的是"全体卡在 backward / TP-AllGather"的排队表象——集体通信超时是 0-size 挂起的下游症状，曾被当成卡点本身；设备级采样（msprof）首次尝试又因参数错误失败，直到改用 task-based 全节点配置才成功捕获卡死窗口内的算子级轨迹（见 3.3）。

4. 一次污染容器实验给出误导性"证伪"：在一次补丁叠加污染（同一块代码多处重复钳位）的容器上观察到"无 0-size 仍死锁"，一度支持"0-size 假设被证伪"的方向。该观察未在干净环境复现、且只覆盖指针面，效力存疑——决定性证据来自干净的栈外最小化 Demo 与验证轮（见 3.4/3.6）。

这四条共同作用，使战役周期被拉长至 14+ 轮。下节的弯路表从工程纪律角度补充逐条教训，本节回答"为什么这么久"的结构性问题。

4.2 模型层 mcore 化: 让标准并行语义作用到模型

4.2.1 问题

MindSpeed-LLM 的训练链路(数据加载、分布式优化器、MoE 专家并行、流水线并行)全部构建在 mcore 并行层语义之上: 张量并行权重按列/行切分、专家权重按 EP 组切分、PP 边界按 stage 传递、SP 在序列维 gather/reduce-scatter。而 GLM-5.3-Flash 官方只有 HF 实现, 没有任何 mcore 并行层——直接套用引擎时模型根本无法装配, 并行语义无处落地。

稀疏层 mcore 版自写(MLA 稀疏注意力 / MoE / topk 路由 / indexer)稀疏层(索引器、池化、稀疏注意力)为模型独有结构, mcore 无对应实现, 无法装配全模型 mcore 化闭环

4.2.3 核心精度修复: fla chunk_kda 原生径 + l2norm 参数修复

KDA 层是 GLM-5.3 混合注意力中计算量最大的部分, 落地采用 fla 0.6.0 的 chunk_kda 原生核路径(而非逐算子拼装)。但全链对拍发现引擎与 HF 参考实现输出相似度仅 0.70, 未达数值门禁。定位与修复:

flowchart TD
    A["引擎 vs HF 对拍<br/>相似度 = 0.70"] --> B["逐层二分定位<br/>KDA 层相似度 = 0.355"]
    B --> C["调用签名核对<br/>use_qk_l2norm_in_kernel 漏传<br/>(默认 False 与模型语义不符)"]
    C --> D["显式传入 True 修复<br/>相似度 = 1.007 ✅"]

根因: 自研 KDA 层调用 chunk_kda 核时漏传 use_qk_l2norm_in_kernel 参数。该参数控制 query/key 的核内 L2 归一化——模型配置需要归一化, 而核默认按"已归一化"处理, 参数漏传导致注意力语义整体错位。修复为显式传 True 后, 对拍相似度由 0.70 升至 1.007(数值门禁判据为 ≥0.995, 已大幅达标)。

指标口径注: 上述对拍数值(0.70 / 0.355 / 1.007)为早期使用的**自定义相似度指标**, 非严格 pearson——pearson 相关系数数学上界为 1.0, 1.007 说明该计算式并非严格 pearson(1.007 为该计算式的计算噪声)。后续门禁统一改用**严格 pearson(np.corrcoef)**, 数学上界 1.0; 当前门禁数值(如 0.999965)均为此口径。
这是全链精度达成的**第一块基石**——此前的训练链路即使跑通, 数值也是错的。

4.3 并行适配: SP 布局迁移与权重桥接根因修复

4.3.1 SP 布局迁移(序列维切分)

问题: 全量并行形态 TP2×EP32 触发 mcore 硬校验"EP>1 × TP>1 必须开启 SP"。而 mcore 的 SP 机制建立在seq 在 dim0 的布局契约上(层输入 [s,b,h], 切分后 [s/tp,b,h]), 自研层原布局为 [b,s,d]——布局冲突, SP 下数值必然错误。

方案: 全模型内部统一迁移到 mcore 的 [s,b,h] 布局, 与框架契约对齐(而非绕过校验)。迁移地图:

组件布局契约迁移动作
embedding 输出SP 下应 [s/tp,b,d]embed 后 transpose(0,1), 用 mcore 的 reduce-scatter embedding
线性投影层(q/k/v/gate/up)输入 [s/tp,b,d], 内部自动 gather直接喂 mcore ColumnParallelLinear, 层输入不做预 gather
fla chunk_kda 调用点核要求 [b,s,heads,d]调用点局部转置回 [b,s], 计算后转回
稀疏索引器(indexer)**需要全序列全局 topk**SP 输入处先 gather 全序列, 池化/全局 topk 语义不被切分破坏
MoE dispatcherSP 感知内置无改动(token permutation 前 gather, unpermutation 后 reduce-scatter)
PP 边界[s,b,hc·d]flatten 后直接传递, 收端按 [s,b,hc,d] view 回

迁移后自研层全面 SP-correct, 全量 TP2×EP32×SP 形态可行。

4.3.2 核心根因修复: 权重桥接 etp 分支

现象: SP 门禁对拍下严格 pearson(np.corrcoef) 0.9606, 未达 0.995——模型前向正确了, 但权重加载链引入了新的偏差。

根因: mbridge 权重桥的基础 load_weights 中, TP scatter 分支(每 rank 从盘加载自己的张量并行切片)只识别了 linear_fc 一类专家键; MoE 的 gate_up_proj/down_proj 两类专家键未归入 EP 感知加载路径——TP scatter 逻辑覆盖了 EP 偏移, 各 rank 加载的专家权重切片位置错位。

修复(桥接核心分支, 补丁固化):

修复前: 仅 ".mlp.experts.linear_fc" 归入 etp 分支 → gate_up/down 走 TP scatter → 覆盖 EP 偏移
修复后: linear_fc + gate_up_proj + down_proj 三类专家键全部归入 etp 分支
        (etp_size=1 时每 rank 按 ep_rank 偏移从盘加载自己的 EP 切片)

结果: 严格 pearson(np.corrcoef) 0.9606 → 0.999965, SP 门禁达成。这是并行适配中价值最高的一处修改——专家权重错位不报错、不崩溃, 只表现为数值偏差, 属于"静默错误", 只有数值门禁才能拦截。

4.3.3 Float16Module 恢复 + e_score 偏置豁免

e_score_correction_bias(专家打分修正偏置)语义上需要保留 fp32 精度: 模型封装层 Float16Module 统一做 bf16 cast 后, 偏置舍入误差足以引起 topk 专家选择翻转。修复为两处配合: ① 桥接加载时豁免该键的 bf16 转换(保持 fp32 落位); ② Float16Module 在 bf16 cast 之后将该偏置恢复为 fp32。价值为精度链补充修复(非主因)。

4.3.4 0-size 输出缓冲 data_ptr 修复(卫生修复)

MoE alltoallv 通信按 sum(output_split_sizes) 分配输出缓冲, 零接收时得到 0-size 张量, data_ptr 可能为 NULL——NPU 侧 AICPU alltoallv 核拒绝空指针, 报 param invalid 并毒化设备流。修复为分配 max(1, sum) 后切片回 0-size(保 numel=0 + 有效指针), 输入侧(反向零接收)同法, 语义零变化。

注意: 这是**指针面卫生修复, 非传输面根因修复**——它只保证 data_ptr 有效, 未触及 0-size 传输在 notify 握手侧的挂起(传输面)。历史上一度有"无 0-size 仍死锁"的观察, 但该观察发生在补丁叠加污染的容器上且仅覆盖指针面, 效力存疑——**指针面排除 ≠ 传输面排除**。传输面由 §4.6 的干净单变量 Demo 与 20/20 验证轮最终定案。此修复消除了一个真实的崩溃触发面(0x2a), 予以保留。

4.6 核心解法: 从"消除 0-size"到"放大 token 量"

4.6.1 现象与根因定案

全量训练在历史阶段反复卡死, 十四轮以上部署未能收敛。经过三轮排除与定案:

步骤内容结论
排除 1fla 核挂起假设: 单卡重放 5 个随机种子全通过, 5 组梯度(q/k/v/g/beta)全有限排除
排除 20-size 输出缓冲**指针面**假设(0x2a): 指针卫生修复运行期生效后仍卡死排除(指针面)——指针面排除 ≠ 传输面排除, 传输面由 Demo+验证轮定案
排除 3张量衔接假设: 契约形状全匹配排除
**定案**msprof 全节点采样: 全体 rank 冻结在 **alltoallv 通信**(Notify_Wait 永不满足); 双节点四 rank Demo 独立复现: 正常场景 1 秒完成, 0-size 场景挂起 5.5 分钟后崩溃**实锤**

机制: 0-size 传输在 NPU 通信栈存在 notify 握手缺陷——发送端反复快速失败, 接收端永久等待 → EP 环上全体互等 → 集群冻结 → 看门狗超时终止。触发条件为 EP32 稀疏路由 + 每 rank 平均 token 数过少: MBS=1 × SEQ=64 时每层全局仅 64 token, 经 32 个 EP rank 均分后每 rank 平均接收 2 token(模型共 288 个专家, 每 rank 持 9 个), "零接收"是实测必现事件——2026-09-05 探针轮 5360+ 次 alltoallv 调用中 4 次零接收(≈7.4e-4/调用), 0-size alltoallv 必然发生。

4.6.2 路线一: clamp 消除 0-size(尝试后回退)

思路: 把 alltoallv 的 splits 中 0 项钳制为 1, 配 dummy token 落位, 从源头消除 0-size 事件。该路线两轮失败:

版本缺陷后果
v1只钳派生值(input_splits), 不钳源值(每个专家的 token 分布)——发送端 splits≥1 但对端 gather 到真实分布(可能 0), **两侧 splits 不一致**通信参数校验失败(0x2a)
v2移到源层面钳制(对称性修复), 但补丁经多次叠加后状态混乱(同一块代码 4 处重复钳位), 其间"无 0-size 事件仍死锁"的观察发生在污染容器上且仅覆盖指针面效力存疑, 不构成对根因的证伪; 传输面由干净单变量 Demo 与验证轮定案; 方案整体回退

结论: clamp 方案不稳定(对称性缺陷 + 补丁状态混乱), 全部回退, 仅保留 §4.3.4 的指针卫生修复。排除口径说明: 指针面排除 ≠ 传输面排除——传输面(notify 握手)由 §4.6.1 的 Demo 与 20/20 验证轮定案。

4.6.3 路线二: SEQ=1024 token 放大——为什么选这条路

概率论证: 0-size 的本质是"小样本量下稀疏路由的必然偶然"。将 SEQ 由 64 放大到 1024(MBS=1), 每层全局 1024 token 经 32 个 EP rank 均分后每 rank 平均接收 32 token(每专家平均约 3.6 token; 按 topk=8 路由展开约 28), 每 rank 零接收的概率按泊松近似为 e^(-32) ≈ 1.3e-14——事件面从"必现"变为"数学上不可能"。运行窗口累积概率: 每 iter 约 2,880 次 alltoallv 调用(45 层 × 32 rank × fwd/bwd), 20 iters 约 57,600 次, 期望零接收事件 ≈ 57,600 × 1.3e-14 ≈ 7×10^-10, 远小于任何工程风险阈值。

决策理由(对领导的正面说明):

1. 不动框架内核: clamp 需要改 MoE dispatcher 的路由语义(引入 dummy token 流), 风险高且验证成本大; 根因解法零内核改动(仅改数据形态参数)——与此前 §4.2-§4.5 的模型/并行/部署适配修改相互独立

2. 从概率根上消除: 不是"修复一次挂起", 而是让 0-size 事件本身不再发生

3. 社区验证同款路径: DeepSeek V4 训练 467 steps 零崩溃, 正是大 batch 下天然规避了该问题——本方案与其同源

4. 代价可控: 收益 = 从概率根上消除 0-size 触发面; 代价为 HBM 升至 ~54GB/卡(64GB 卡的 84%)与短样本 padding 计算开销(SFT 数据无打包逻辑, 短样本按定长 1024 补齐, 计算被 loss_mask 屏蔽)

结果: 20/20 iters 完整跑通、loss 9.77→0.083 整体收敛(117 倍)、0 崩溃 0 卡死。

4.7 弯路复盘(诚实记录)

本章探索过程中的弯路（clamp v1 对称性缺陷、clamp v2 补丁状态混乱、节点排查错误归因、一次改两个变量）与第 3 章 §3.7 的结构性复盘、§3.8 的弯路表同源, 此处不重复展开, 完整归因与逐条教训见该两节。仅保留两条工程结论:

  • **涉及配对侧（通信 splits/布局）的修改必须静态审查两侧对称性**, 凡发送/接收成对的参数, 先审两侧一致性再部署;
  • **补丁必须幂等并在干净容器验证**——从零还原（§4.5 R6 一键还原）是唯一可靠基线, 叠加补丁的状态不可复现。

5.4.2 门禁意义解读(面向领导)

四道门禁从"能不能训"到"训得有没有效"逐层递进, 每道门禁回答一个独立问题:

1. FULL8_TRAIN_GATE(已 PASS)——"这套系统真的能训吗?"

证明 64 NPU 跨 8 节点的全量训练链路(前向/反向/优化器/专家并行通信/流水线)物理可运行且数值稳定: 20 个迭代无 NaN、无梯度丢失、无崩溃。这是任何训练结果可信的前提门槛——跑不通或数值溢出, 后面的一切结论都无从谈起。

2. 收敛性(已 PASS)——"loss 下降是模型真的在学习, 还是噪声?"

117 倍收敛 + 对数尺度匀速下降 + 梯度范数同步收敛, 三者共同证明 loss 下降是优化器对真实梯度的响应, 而非随机波动或实现缺陷下的巧合。这是从"系统能跑"到"系统在正确学习"的关键一步。

3. FULL8_PEARSON(暂缓)——"训练曲线可信吗? 引擎实现与标准实现一致吗?"

回答"引擎的数值实现是否忠实于模型定义"——逐层对比引擎与 HF 标准实现的前向输出, 要求严格 pearson(np.corrcoef) ≥ 0.995。该门禁在减层规模 SP 配置下已实测 0.999965(远高于阈值), 全量规模尚未执行, 属工程性延迟而非已证结论。补做三要素如下:

  • **成本(一次性, 约 4 小时)**: 参考链二次加载 643GB 权重(单流 NFS, 3h+)+ 全量前向对拍(321.32B CPU bf16 前向, 分钟~半小时级);
  • **低风险依据(推断, 非实测)**: ①减层规模 SP 同门禁 0.999965 达成(权重加载 etp 分支与 SP 布局同链验证); ②全量 20 iters 全程 0 NaN; ③loss 收敛与 grad norm 同步下降, 梯度信号真实; ④首 iter 对拍 dump 已落盘, 结果可复算;
  • **补做计划**: ThreadPool 并行分片加载已实现(可将权重加载压至 1~2 分钟), 本版本未启用; 补做路径已存在, 建议在进入更长训练前安排一次全量 pearson 对拍确认。

因此"全量风险低"为推断结论(基于上述依据), 非实测结论; 该门禁不阻塞训练链推进。

4. GSM8K EM(待执行)——"训练带来了真实的业务价值吗?"

最终判据: SFT 前后模型在 GSM8K 数学推理任务上的准确率对比(后 > 前)。从"系统在正确学习"到"学习结果有业务价值"的最后一公里。预期管理: 当前训练窗口仅 20 iters(640 samples, 约占 GSM8K 训练集 9%), 能力提升信号预期较弱; GSM8K 对比门禁将在更长训练(如数百 iters)后执行, 本次仅确认评估链路可用。

门禁总评: 训练链三道技术门禁已通过两道, 第三道为工程性暂缓; 唯一未执行的能力门禁(GSM8K)脚本已就绪。整体判定: GLM-5.3-Flash 全量 SFT 训练链验证达成, 具备进入更长训练与下游验证的条件。

6.3.3 优化空间(按收益排序, 均待专项验证)

1. HBM 占用 84%(~54GB/64GB)偏高【实测】——最高优先级

当前 recompute 全关、激活全驻留。风险: SEQ 1024→2048 时 HBM 预计逼近上限。方向: ①选择性开启 recompute(fla 核已证实可重算, 需对账 SP 通信流序——曾因 checkpoint 重放与 EP 通信冲突死锁而全关, 需在重算位置与流序上专项验证); ②PP 切分调优(45 = 22+23 非均匀, 探索 23+22 或 3 段); ③激活内存优化(MBS 相关)。

2. 首迭代 345s 的 JIT 编译成本: 一次性开销, 复跑建议持久化 triton_ascend kernel cache, 可将冷启动降到 ~90s 量级【估算】。

3. 权重加载慢 rank 305s: 643GB 单流 NFS 读取拖尾, 并行分片加载(ThreadPool)方案已就绪未启用, 预计可压至 1~2 分钟【估算】。

4. 算子融合与通信重叠: 当前 fla 稀疏核已走 triton_ascend 原生径(chunk_kda 前反向 + l2norm 融合), 进一步可做: MoE alltoallv 与 GEMM 计算重叠、PP 边界通信与计算重叠; MFU 尚未实测(需 msprof 专项), 建议下一步基准补齐。

5. batch 形态: MBS=1 下 PP=2 流水线 bubble 占比高; 在 HBM 允许范围内提升 MBS(如 2)可同时改善流水线效率与吞吐【估算, 需 HBM 复核】。

6. iter 14 的 95.8s 尖峰: 孤立事件, 长跑(数百 iters)时需观察频率, 若密集出现则排查节点间网络/NFS 抖动。

  • **实测基准**: 全量 321.32B 模型 64 NPU 训练, 稳态 **89.4s/iter**, 聚合吞吐 **366 tok/s**, HBM 峰值 **~54GB/卡(84%)**, 训练阶段 20 iters 全程 34 分钟, 0 异常。
