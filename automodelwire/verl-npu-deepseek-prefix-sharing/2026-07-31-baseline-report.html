概述

在 2 节点 Ascend 910B (16 NPU) 上用 4 层 DeepSeek V4 Flash 代理模型 + 真实 BF16 权重 (symlink)， 跑通了完整的 verl GRPO RL 训练管线: vLLM rollout → reward → log_prob → advantage → actor update → HCCL 权重同步。 14 轮部署, 解决 10 个 bug, 最终 9 steps 稳态完成。

核心结论
mbridge + vLLM + MindSpeed-LLM + HCCL 全链路在 Ascend NPU 上可打通。训推分离 (112 训练 + 155 推理) 架构可行, 权重跨节点广播 15-16s/step 正常。

Bug J 深度分析 (最昂贵)

占 14 轮中的 7 轮, 根因是 Ascend NPU 已知的设计选择 (Triton = identity decorator)。

错误路径: J v1 (PyTorch) → RuntimeError → J v2 (reshape) → RuntimeError → J v3 (max_num_blocks) → IndexError → J v4 (复用 CP>1 path) → ✓
选了"从零实现"而非"复用已有"的策略。每次修复只解决暴露的一个边界问题, 没有意识到 vllm-ascend 已有 CP>1 的 _compute_pcp_dcp_slot_mapping 纯 PyTorch 实现完全可复用。

下次如何避免: 修复前先搜索项目中是否有类似功能的已有实现; 自研迭代 2 次无果 → 停线, 切换策略 (元规则 C); 优先问"这段逻辑在其他配置下是否已有工作实现?"

模式级教训

串行试错的低效
核心问题: 看到错误 → 立刻改代码 → 部署验证 (7 分钟起跳) → 看下一个错误。
应该是: 每个错误 三问 (说啥/合理吗/根因在我改的东西里吗) 后才动手。
多 bug 同源找共同假设
D/E/F/G/H 同属"训推分离架构假设不完整", 应一次性解决而非逐个修。
可行性硬约束先算清
模型大小 vs HBM: 4-node 数学不可行在首轮就应通过算术排除, 而非实测 OOM 6 次。
