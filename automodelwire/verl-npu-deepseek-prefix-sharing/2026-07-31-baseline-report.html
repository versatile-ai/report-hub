3. 4 层代理模型: 零拷贝构建机制

3.1 核心原理

DeepSeek V4 Flash 完整模型有 43 层, ~567GB BF16 权重。直接 2 节点 16 NPU 跑全参数学不可行 (单卡 59.8GB > 61GB HBM)。 但 mbridge 和 vLLM 都是按需加载 — 只遍历模型结构中的参数名而非 safetensor 里的全部 key — 所以可以把 43 层的权重文件放在那里, 只让模型"看到"前 4 层。

关键认知
不需要裁剪权重文件。safetensor 里 43 层权重全在, 但模型只请求 model.layers.{0..3}.*, safetensor IO 只读对应切片。这也是为什么可以用 symlink — 零拷贝, 不修改原始权重目录。

3.2 构建步骤 (5 步)

1 rsync 非权重文件 (config.json, tokenizer, modeling *.py)
从 /data/model/DeepSeek-V4-Flash-bf16-deploy/ 复制到 mini_model 目录, 排除所有 *.safetensors。 config.json 会拷贝但随后被 patch。
2 ln -sf 权重文件 (零拷贝 symlink)
每个 *.safetensors 从真实模型目录 symlink 到 mini_model 目录。 不复制, 不修改, 不裁剪。后续任何按需加载只读对应参数切片。
3 cp index.json (必须复制, 不能用 symlink)
model.safetensors.index.json 包含 weight_map (参数名 → 文件名映射)。 必须 cp (不可 symlink), 因为下一步要过滤 weight_map 移除 layers ≥ 4 的条目, symlink 会穿透修改原始权重目录, 不可逆破坏 43 层真模型。
4 Patch config.json
设置 num_hidden_layers: 43 → 4, num_nextn_predict_layers: 1 → 0 (MTP 引用 layer 43, 4 层下不存在), 截断 compress_ratios 列表到前 4 层对应条目。
5 过滤 index.json weight_map
用正则 r'^layers\.(\d+)' 匹配所有参数名, 移除 layer ≥ 4 的条目。 这一步至关重要: vLLM 加载时遍历 weight_map 的全部 key, 若保留 layer 4-42 的映射, 会导致 KeyError (4 层模型没有 model.layers.4 模块)。 mbridge 则不受此影响 — 它通过 mcore model.named_parameters() 遍历, 只有 4 层的参数名。

3.3 为什么 mbridge 只加载 4 层

mbridge 的权重加载流程: 

# bridge.py:load_weights (第 147-269 行)
# 1. 遍历 model.named_parameters() → 只有 4 层的 local param names
# 2. local_to_global_map: decoder.layers.{0..3}.xxx
# 3. _weight_name_mapping_mcore_to_hf: 映射到 HF 名称 layers.{0..3}.xxx
# 4. safetensor_io.load_some_hf_weight: 只从磁盘加载这些 key 对应的 tensor
# 5. _weight_to_mcore_format + TP/EP scatter: 加载到 mcore model

结论: mbridge 不需要任何特殊处理就能只加载 4 层 — 它跟着模型结构走, 模型有几层就加载几层。

3.4 为什么 vLLM 只加载 4 层

vLLM 的加载路径不同: 

# vLLM 加载: 遍历 model.safetensors.index.json 的 weight_map
# 如果 weight_map 包含 layers.4.* → 尝试加载到 model.layers.4 → KeyError
# 所以必须过滤 index.json 的 weight_map (步骤 5)

差异: mbridge 由 mcore model 驱动加载, 自然只请求 4 层参数; vLLM 由 index.json 驱动加载, 必须过滤 weight_map。 两者的模型结构本身都只有 4 层 (config.json num_hidden_layers=4), 所以都不会请求 layer ≥ 4 的权重。

4. mbridge: 4 层模型下的权重桥接

4.1 mbridge 在基线中的角色

mbridge 是 mcore (MindSpeed-LLM/Megatron-LM 训练侧) 和 HF (vLLM 推理侧) 之间的权重转换桥梁。 训练侧用 Megatron 格式的参数名和 TP/EP 切分, 推理侧用 HuggingFace 格式的完整参数。 mbridge 在两端之间做:

  • load_weights (HF → mcore): 训练初始化时, 从 HF safetensor 加载权重到 mcore 模型, 同时做 TP 切分和 EP 散布
  • export_weights (mcore → HF): 每个训练 step 结束时, 把 mcore 模型权重导出为 HF 格式, 经 HCCL 广播给推理节点
  • name mapping: 维护 mcore 参数名 (如 self_attention.linear_q_up_proj.weight) 到 HF 参数名 (如 layers.0.attn.wq_b.weight) 的映射表

4.2 4 层模型带来的变化

4 层模型对 mbridge 本身没有特殊要求。mbridge 通过 model.named_parameters() 遍历参数, 模型有几层就处理几层的权重。配置文件 config.json 的 num_hidden_layers=4 驱动 Megatron 构建 4 层模型, mbridge 自然只看到 4 层的参数。

但 DeepSeek V4 Flash 的独特架构 要求 mbridge 新增大量映射。这是模型架构带来的, 与层数无关 — 即使跑 43 层全参, 这些映射同样是必需的:

4.3 deepseek_v4 模型类型注册

register_dsv4.py
作用: 把 DeepSeek V4 的自定义 DeepseekV4Config 类注册到 HuggingFace transformers 的 AutoConfig 注册表。 从 $MODEL_PATH/config.json 读 auto_map.Config 字段, 动态 import configuration_deepseek_v4.py 模块, 调用 AutoConfig.register("deepseek_v4", cls)。
为什么需要: DeepSeek V4 Flash 的 config.json 中 model_type: "deepseek_v4" 不是 transformers 原生支持的模型类型。 不注册会导致 AutoConfig.from_pretrained() 抛出 Unknown model type 错误, 整个 mbridge 初始化链断裂。
patch_dsv4_config.py
作用: Monkey-patch DeepseekV4Config.__init__, 在初始化完成后补充 20 个镜像内配置文件缺失的属性。 包括 MLA 参数 (kv_lora_rank, q_lora_rank, qk_head_dim, v_head_dim...)、 attention 参数 (multi_latent_attention, qk_layernorm, use_g2_attention...)、 MoE 参数 (intermediate_size, enable_dsa_indexer, enable_mhc...)。
为什么需要: DeepSeek V4 Flash 的 config.json 不包含这些字段 (上游 modeling code 用默认值)。 但 mbridge _build_config 显式引用 hf_config.q_lora_rank、hf_config.kv_lora_rank 等, getattr 默认值不可靠。patch 确保所有被引用的属性都有确定的值。 Bug F/G 间接相关 — 如果 MLA 参数缺失, mbridge 构建的 mcore config 不正确, 后续权重映射错位。
deepseek_v4_init.pth
作用: Python sitecustomize .pth 文件。在 Python 启动时自动 import register_dsv4, 确保 AutoConfig.register 在任何模型加载代码执行前完成。
为什么需要: Ray worker 进程启动时无法控制 import 顺序。通过 .pth 文件在 site-packages 初始化阶段注入, 保证 vLLM/mbridge 的 from_pretrained 调用时 deepseek_v4 已注册。

4.4 DeepSeek V4 完整权重映射 (deepseek_v3.py)

mbridge/models/deepseek_v3.py
作用: 这是 mbridge 对 DeepSeek V4 最核心的修改。定义一个 DeepseekV3Bridge 类 (用 @register_model(["deepseek_v3", "deepseek_v4"]) 注册), 实现完整的 mcore ⇆ HF 权重名映射。包含:
  • _DIRECT_MAPPING: 6 个直映射 (embedding, final_layernorm, output_layer, hc_head)
  • _MLP_MAPPING: 13 个 MLP 参数映射, 含 MoE expert (正则匹配 mlp.experts.local_experts.{N}.linear_fc1.weight) 和 MHC (hc_base/hc_scale/hc_fn)
  • _ATTENTION_MAPPING: 20 个 attention 参数映射, 覆盖 MLA q/kv/o projections、q/kv layernorms、compressor、DSA indexer
  • _build_config: 从 HF config 构建 MLATransformerConfig (mcore 0.12 MoE + MLA + MTP 配置)
  • _get_safetensor_io: BF16 权重直接走 SafeTensorIO (非 FP8), 绕过 DequantFP8SafeTensorIO 以避免 triton ascend 后端 import
  • _weight_name_mapping_mlp: 正则匹配 + 模板替换 (支持 expert_id 捕获组), 替代父类简单的关键字匹配
  • _convert_mtp_param: MTP layer 参数映射 (仅支持 61 层 + 1 MTP layer, smoke test 中 MTP 已禁用)
为什么需要: 父类 LLMBridge 只有 Dense 模型的 attention/MLP/direct 三组默认映射, 完全不适用 DeepSeek V4 的 MLA + MoE + MHC + DSA indexer + compressor 架构。 没有这些映射, 权重加载时所有参数名都无法匹配 → 每个参数抛 NotImplementedError。

4.5 bridge.py 核心修改

mbridge/core/bridge.py
4 处关键修改:
  1. load_weights norm bias 预过滤 (第 166-176 行): 加载时跳过以 .bias 结尾的参数。 Megatron persist_layer_norm=True 会创建零填充的 RMSNorm bias, 但 HF 权重中从不存储这些 bias (FP8→BF16 转换时丢失)。不跳过会导致 safetensor key not found。
  2. load_weights ETP=1 broadcast 替代 scatter (第 222-230 行): 原逻辑只在 ETP > 1 时 scatter, ETP=1 时直接 copy。现在 ETP=1 时也 broadcast (从 etp_rank 0 到全 etp_group), 确保所有 etp rank 都有完整 expert 权重。
  3. export_weights EP all_gather + 双格式 expert ID 解析 (第 387-443 行): 训练侧 EP=4 切分 expert, 推理侧需要完整 expert 权重。 对每个 local expert, all_gather 从 4 个 EP rank 收集权重片, 然后解析 expert ID — 支持两种格式: Form A (TP=2/ETP=2, expert ID 嵌在路径 local_experts.{N}.) 和 Form B (TP=8, expert ID 作为 suffix .weight{N})。 Bug F/G 修复
  4. _weight_merge_across_tp 1D tensor fallback (第 932-946 行): num_distributed_optimizer_instances=1 展平所有参数到 1D buffer 时, dim=1 cat 会 IndexError。改为 dim=0 cat 兜底。 Bug H 修复
为什么需要: 修改 1 (norm bias) 是通用问题, 所有 Megatron 模型都有。修改 2-4 是 DeepSeek V4 + NPU 特有问题: EP 切分 + 双格式 expert ID 是 DSv4 MoE 架构的产物; 1D buffer fallback 是 MindSpeed 分布式优化器 num_instances=1 的副作用。
mbridge/core/llm_bridge.py
作用: LLMBridge 基类, 大部分是上游模板代码。关键修改在 _build_base_config — 添加 expert_tensor_parallel_size、context_parallel_size 等并行参数, 以及支持字符串格式的 attention_backend (自动转 AttnBackend enum)。 _get_transformer_layer_spec 增加 vp_stage 参数兼容 mcore 0.12。
为什么需要: 上游 mbridge 只考虑 TP/PP/EP, 不包含 ETP、CP 等 NPU MindSpeed 特有的并行维度。 缺少 ETP 会导致 expert tensor parallel 配置为 0 → 后续权重切分逻辑错误。
mbridge/models/ext/deepseek_v3/dequant_fp8_safetensor_io.py
作用: FP8 safetensor reader — 支持从 safetensor 加载 FP8 权重并用 scale_inv 做 dequant。 关键修改: 将 safe_open 的 device 从 CPU 改为 "npu" (NPU 直接读, 避免 CPU→NPU 拷贝), 设置 torch.set_default_dtype(torch.bfloat16)。
为什么需要: 虽然本次测试用的是 BF16 权重 (走 SafeTensorIO, 不经过此类), 但代码路径判断 self.dtype == torch.bfloat16 决定是否使用此类 (deepseek_v3.py 第 367-372 行)。预备 FP8 权重加载能力。

9. 39 文件 Overlay 逐文件分析

39 个文件覆盖 5 个组件。下面按组件分组, 每个文件说明: 修改了什么 (具体代码变更) / 为什么需要 (不修改会怎样) / 关联 Bug。

9.1 Megatron-LM (3 文件) — 分布式训练框架适配

Megatron-LM/megatron/core/optimizer/distrib_optimizer.py
修改: 设置 num_distributed_optimizer_instances=1, 展平所有参数到 1D buffer (而非默认 2D buffer)。
为什么: 降低优化器内存开销。副作用是参数变为 1D tensor, 后续 weight merge/split 逻辑需要 1D 兼容 (bridge.py 的 1D fallback 即为此)。 Bug H 间接因素
Megatron-LM/megatron/core/pipeline_parallel/p2p_communication.py
修改: NPU 设备适配 — 将 torch.cuda 调用替换为 torch.npu (current_device, Stream, etc.)。PP=1 时此文件不被调用, 但作为基础设施保留。
为什么: 上游 Megatron-LM 只支持 CUDA。Ascend NPU 上必须替换所有 cuda API。
Megatron-LM/megatron/core/transformer/transformer_config.py
修改: 增加 DeepSeek V4 特有的 Transformer 配置字段支持: multi_latent_attention, enable_dsa_indexer, enable_mhc, use_g2_attention 等。
为什么: Megatron-LM core_r0.12.0 的 TransformerConfig 不包含这些 V4 Flash 专属字段, 没有它们模型构建时会使用默认值 → 模型结构与权重不匹配。

9.2 MindSpeed-LLM (7 文件) — 训练算子 NPU 适配

MindSpeed-LLM/megatron/core/optimizer/cpu_offloading/hybrid_optimizer.py
修改: Hybrid optimizer (CPU offload) 的 NPU 适配 — 优化器状态从 NPU 拷贝到 CPU 时使用 torch.npu 同步原语。
为什么: 训练 HBM ~50GB, 优化器状态 ~8GB, 必须 CPU offload 才能满足 61GB 约束。不修此文件会导致优化器 step 时 NPU-CPU 同步失败。
MindSpeed-LLM/mindspeed_llm/pretrain_deepseek4.py
修改: DeepSeek V4 的 model_provider 函数 — 构建 Megatron GPTModel 所需的 transformer_layer_spec (含 MLA attention + MoE + MHC)。

10.9 逐文件根因分析: 为什么"不新增就不可行"

以下对 17 个新增修改逐一做根因级审查。每个文件回答: 上游代码的假设是什么？该假设在本环境中如何被打破？参考实验的已有方案为什么不能直接复用？ 根因分四类: A — CANN 版本断崖变化, B — persist_layer_norm 连锁反应, C — 模型/镜像差异, D — NPU 专用功能补全。

类别 A — CANN 9.0.0 → 9.1.0-beta.3 的断崖式变化 (3 文件)
这是最大的差异来源。CANN 在两个关键维度上行为相反: HCCL 端口分配策略和 Triton Ascend backend 的 JIT 能力。
block_table.py — Bug J 核心修复
上游假设: _compute_slot_mapping_kernel 是被 @triton.jit 编译的 GPU kernel, kernel[(grid,)] 语法是合法的 Triton kernel launch, 调用 __getitem__ 触发 JIT 编译和执行。

假设如何被打破: CANN 9.1.0-beta.3 的 Ascend Triton 实现为: 
def jit(fn=None, **kwargs):
    def decorator(fn):
        return fn  # 原样返回, 不编译
因果链: @triton.jit → 普通 Python 函数 → f[(grid,)] → __getitem__ 对 function 对象 → TypeError: 'function' object is not subscriptable。 这不是"性能退化", 而是 API 契约破坏——Triton 的编译 promise 被完全跳过, 导致 vLLM 的 kernel launch 语法不合法。

为什么不能复用参考实验: 参考 CANN 9.0.0 的 Triton Ascend backend 能通过 JIT 编译 (kernel 虽性能退化但语法不崩), 且参考实验使用的社区 verl_patches.tar.gz 已包含 block_table 补丁。 但该补丁针对 vLLM 0.22.1 的 block_table 架构——vLLM 0.23.0 重构了 MultiGroupBlockTable + _compute_pcp_dcp_slot_mapping 路径, 0.22 的补丁不兼容。两个维度叠加: Triton 版本 × vLLM 版本 → 无现有方案可参考, 必须全新实现。

修复逻辑: 发现 CP>1 路径的 _compute_pcp_dcp_slot_mapping 已是纯 PyTorch (index + mask + scatter), 让 CP=1 退化到 total_cp_world_size=1 走同一条 PyTorch 路径, 与 Triton 完全解耦。 P0 — 不新增必崩溃
constants_ppo.py + vllm_rollout/utils.py — Bug E 核心修复 (HCCL 端口策略)
上游假设: 参考 CANN 9.0.0 + A2 上, HCCL_HOST_SOCKET_PORT_RANGE=auto 与 MC² 算子不兼容, 必须在 vLLM worker 内 os.environ.pop() 掉。

假设如何被打破:
  1. CANN 9.1.0-beta.3 修复了 MC² 与 auto port 的兼容性 (同事已验证)
  2. 但 9.1.0-beta.3 引入新行为: HCCL_IF_BASE_PORT=60000, isAutoPort[0]=hardcoded (不递增)
  3. 训推分离架构下, 节点 155 device 0 上同时存在两个 HCCL communicator:
    • vLLM node-internal comm (ranks[8], root=155)
    • checkpoint engine cross-node comm (ranks[9], root=112)
  4. 两个 comm 默认都绑定 port 60000 → HCCL resource unavailable
为什么不能复用参考实验: 参考实验的 "pop auto" 在 9.1.0 上产生 完全相反的效果——pop 掉 auto 后回退到 hardcoded port=60000, 两个 comm 必然冲突。参考实验的修复对 9.1.0 是 投毒而非解药。

证据: constants_ppo.py 追加注释中有明确的技术判断链—— "cann-9.1.0-beta.3 恰相反, 需保留 auto"、 使用 HCCL_ENTRY_LOG_ENABLE 而非 9.0.0 的 HCCL_DEBUG (libhccl.so 不解析旧名)。 这是 基于源码级证据的版本差异判定, 不是猜测。 P0 — 不新增必崩溃
类别 B — persist_layer_norm=True 的连锁反应 (2 处)
Megatron 的一个性能优化开关在权重导入/导出路径上创建了 HF 格式中不存在的"幻影参数"。 参考实验未触发此路径 (默认 False)。我们设为 True (NPU 上性能优化), 必须配套过滤。
bridge.py — norm bias 预过滤
上游假设: _weight_name_mapping_mcore_to_hf 能为 model.named_parameters() 中的每个参数找到 HF safetensor 中的对应 key。

假设如何被打破:
  1. deepseek_v3.py:_build_config 设 persist_layer_norm=True
  2. Megatron 为每个 RMSNorm 层创建零填充的 .bias (如 decoder.layers.0.self_attention.q_layernorm.bias)
  3. 这些 bias 出现在 model.named_parameters() 中 → mbridge 尝试加载 → 在 safetensor weight_map 中查找 → 不存在
  4. HF RMSNorm 从不需要 bias (只有 weight, 无 bias)
因果链: persist_layer_norm=True → Megatron 创建幻影 bias → mbridge 查找 HF 映射失败 → KeyError。

为什么参考实验未触发: 参考实验 没有设 persist_layer_norm=True (mbridge.patch 中 _build_config 无此字段, Megatron 默认 False)。 无此参数 = 无幻影 bias = 不需要过滤。我们设了此参数 (避免每 step 重分配 norm 内部 buffer), 就必须配套过滤。

为什么必须设 persist_layer_norm=True: NPU 上每次 H2D/D2H buffer 重分配有 ~100ms/层开销。对 4 层 85s step 影响不大, 但对 43 层全参后续实验, 累积开销不可忽略。此参数是 面向全参实验的预埋。 P0 — 不新增必崩溃
bridge.py — 1D tensor fallback (Bug H)
上游假设: _weight_merge_across_tp 中的 torch.cat(mcore_weights, dim=1) 对所有 MoE 参数有效。

假设如何被打破:
  1. distrib_optimizer.py 设 num_distributed_optimizer_instances=1 → 展平到 1D gradient buffer
  2. export_weights → _weight_merge_across_tp 对 linear_fc2.weight 执行 dim=1 cat
  3. 1D tensor 没有 dim=1 → IndexError
修复: 检测 1D tensor → fallback 到 dim=0 cat。

13.2 法则 1: 动手前必过的 5 道数学关

在第一次部署之前, 用计算器算清以下 5 个硬约束。任何一个不满足, 部署是浪费时间。

① HBM 容量约束
权重 + 梯度 + 优化器 + KV cache + 运行时 < 61GB
权重 = total_params × dtype_size / (TP × PP × DP)
梯度 = 同上 (不 offload 时)
KV cache = block_size × num_blocks × num_layers × num_heads × head_dim × 2 (K+V) × dtype_size
运行时 ~ 10-15% 权重 (经验值)
本次教训: 4 节点 43 层 = 单卡 59.8GB > 61GB 可用, 2 行计算 5 分钟排查, 实测花了 2 天。
② 并行度整除约束
num_experts % EP == 0 且 num_heads % TP == 0 且 num_layers % PP == 0
本次教训: 43 是质数, PP > 1 时层数无法均分, PP=2 因 ETP(64) > world_size(32) 不可行。 Kimi K3 特化: 896 experts = 2^7 × 7, EP 可取 {1,2,4,7,8,14,16,28,32,56,64,112,128,224,448,896}。93 层是奇数, PP 需特别处理。
③ ETP 约束
expert_tp × EP ≤ world_size
本次 TP=1, ETP=2, EP=4 → 2×4=8 ≤ 8 ✓。但 PP=2 时 ETP 需求翻倍。
④ 数据集适配
MAX_PROMPT_LENGTH ≥ max(prompt_ids_len)
本次教训: 凭假设设 MAX_PROMPT_LENGTH=32, 实际 GSM8K mean=83, max=171。应该先用 tokenizer 跑一次:

5 分钟排查, 本次花了 3 轮 ~6h。
⑤ 推理并行约束
GEN_EP == GEN_TP × GEN_DP
本次 8 == 8×1 ✓。每次改 EP 必须同步调整 TP 或 DP。
方法: 5 分钟 HBM 计算表
任何新模型/新集群组合, 在讨论方案之前先算清这个表。数字填进去, 约束自然暴露。
