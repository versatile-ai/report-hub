定位与代码来源

两者对「官方只发布了推理参考实现、没有可训练 modeling」这一前提，给出了相反的工程回答。

torchtitan-npu：自研 torchtitan-native 实现
  • 模型层落在 torchtitan_npu/models/deepseek_v4_1/，继承 torchtitan 的 Decoder 与 models/common 公共组件（RMSNorm、ComplexRoPE、MoE 工厂），配置走 config_registry.py（9 个模型 flavor + 3 个 LoRA flavor）。
  • 跨层状态（压缩 KV、index keys、候选池、student logits）作为显式前向参数逐层传递，不留全局可变缓存；packed 文档由 DeepSeekV41Metadata 统一描述，参考核与融合核读同一份元数据。
  • NPU 能力与模型层解耦：override/deepseek_v4_1/ 无 __init__.py，导入不注册任何条目，全部经 --override.imports 写完整 module.function 显式启用。
FSDPTurbo：vendored 复刻官方参考实现
  • 官方仓只发布 inference/model.py 等参考源码，FSDPTurbo 将其按固定 revision（dba1be0a）复制进 fsdp_turbo/models/deepseek/deepseek_v41/，保留原组件命名与 checkpoint 键路径，剥离了推理 TP 分支与全局 rank 状态。
  • 跨层状态走 runtime.py 的全局单例 shared_attn（source 层写、consumer 层读，每步 reset）；attention_mask/sfa_layout/cu_seqlens 经前向参数显式传递。
  • 训练能力由 adapter.py（DeepseekV41ForCausalLMAdapter）包装：构造期校验（BF16 强制、MTP/DSpark 拒绝），图文 causal-LM loss 接口，chunk loss 装配。
这一选择的直接后果：torchtitan-npu 与 torchtitan 的训练器、compile、并行栈深度耦合，可整图编译入图，但升级要跟着上游走；FSDPTurbo 与官方推理实现逐行对应、便于对照升级，但全局共享 runtime 使 attention 无法 recompute，也无法接 torch.func 之外的分块求导方案。

共同点

两边在「模型结构、算子生态、平台分档、Engram 存储、参考对照」五个层面高度一致。

组件结构对齐官方发布配置

均实现 CSA2 稀疏注意力（latent attention + 滑窗 + 压缩条目 + sink）、Lightning Indexer 两级 top-k、Compressor softmax 门控 KV 池化、Single-Pass mHC（hc_mult=4、Sinkhorn 20 迭代）、MoE 384+1 专家 top-6（sqrtsoftplus 打分 + noaux correction bias）、Engram n-gram 哈希记忆（第 1/14 层，约 3.84 亿行/表）与 ViT 图文塔，对齐 HF config.json（40 层 / hidden 5120 / moe_inter 2304）。

均不做 MTP / DSpark 训练

torchtitan-npu 在 readme 中明确未实现；FSDPTurbo 保留了推理结构代码（dspark.py），但训练期构造校验直接拒绝（adapter.py 的 _validate_training_args）。

同一 CANN 融合算子生态

SparseFlashMla、Lightning Indexer、Compressor、MhcPreSinkhorn/MhcPost、EngramFetch/ElasticBuffer、视觉 FlashAttention 均来自 cann_ops_transformer / torch_npu 系列，且都做成「可选开关 + eager 参考回退」，关闭开关即回到纯 PyTorch 路径。

A3 / A5 双平台分档

各自提供 Atlas A3（Ascend 910_93 / 910B / 910C）与 Ascend950DT（A5）两套配置与融合栈，按 NPU 型号选择实现；A5 档普遍启用更多量化与融合特性。

Engram Host-offload + 活跃行稀疏更新

哈希表权重 BF16 驻 CPU pinned memory、Adam moment FP32，稀疏梯度只触达活跃行；表沿 EP 切行、副本共享行分片，行数按 2048 对齐以便 EP 等分。

图文多模态联合训练

ViT 与语言塔联合反传，均在 processor / 协议层适配 DeepSeek 图文 token 协议；视觉注意力有 NPU 融合路径（torchtitan-npu 走 SDPA 自动路由 FA，FSDPTurbo 走 FlashAttentionScore/Grad 算子）。

参考路径作为数值对照

torchtitan-npu 用 USE_GOLDEN=1 切纯参考栈、--debug.seed/--debug.deterministic 做精度对照；FSDPTurbo 关闭全部融合开关即回退 eager 实现。两边都把 PyTorch 参考实现当作精度基线而非仅 fallback。

HF 初始化 + DCP 续训双轨 checkpoint

均支持 HF safetensors 权重初始化与 torch DCP 断点续训；Engram 表以全局逻辑行保存（不含本地 padding），支持 EP 分片的导入导出。

单序列 packed 训练形态

local batch / MBS 固定为 1，一条 packed 序列含多篇文档；多文档边界 label 置 −100，文档间注意力与位置编码相互隔离。

差异点（分维度）

按十个维度展开：每个对照点给出两侧机制与设计决策，并在「影响与训练优缺」列给出该差异在训练场景下的影响及各自得失。蓝点＝torchtitan-npu，橙点＝FSDPTurbo；「优/缺」为该侧在训练中的优势与代价。

优参考核与融合核读同一份元数据——同一形状下双栈精度对照成本极低，且这正是其数值验证体系的地基；AI_CPU metadata 每微批预计算一次，摊薄了逐层调度开销

缺契约复杂（frames + pytree 注册 + 构造期校验），新算子接入门槛高

优实现直白、单算子调试路径短

缺各算子调度参数自建，多算子协同（TND + 融合压缩/LI）时契约易不一致，README 也据此禁止了这批组合——融合能力被元数据短板拖累
契约校验 构造期检查融合对：SMLA 与 LI 两个 override 必须同开（SMLAG 反向产出教师信号 p，SLIKG 反向消费），单开任一侧直接 ValueError adapter 构造期校验 dtype/expert_dtype/MTP/DSpark；不支持的开关组合（CP + chunk_loss、TND + fused compressor/LI）在配置初始化时拒绝

优把「训练信号是否正确」前移到构造期：杜绝单开 LI 时 indexer 全程不更新、单开 sparse-attn 时教师信号错误这类静默精度事故，长训中这类事故的代价远大于报错本身

优组合合法性全部在配置层拦截，报错直接指向开关名，排障快

缺禁止组合偏多（如 CP 下关闭全部融合），可用配置空间明显小于 torchtitan-npu

接入与配置方式config & launch

torchtitan-npu
  • 启动：--module torchtitan_npu.models.deepseek_v4_1 --config <flavor>，脚本经 scripts/run_train_multinodes.sh。
  • NPU 能力逐个显式启用：--override.imports torchtitan_npu.override.…；A3/A5 脚本组织默认融合列表，末尾 CLI 覆盖；显式传入会整体替换集合。
  • 量化：--extension.quantization.enable-quantized-training --extension.quantization.recipe all_block_fp8（A5 默认）。
FSDPTurbo
  • 启动：run.sh → torchrun → train.py --config config_A5.yaml。
  • 三份 YAML（A3/A5/TND）+ model_config/ 5 份结构 JSON；并行由 fsdp_plan/tp_plan/ep_plan/cp_plan 声明。
  • 融合为 YAML 布尔开关：use_sparse_flash_attn、use_fused_lightning_indexer、use_fused_compressor、use_fused_mhc、use_triton_inplace_rope 等。
影响：CLI 显式启用使每次运行的 NPU 能力组合随命令行留痕、可复现可审计，适合 recipe 化的预训练流程；但融合列表写错一个模块名即启动失败，新用户上手成本高。
影响：YAML 声明式 plan 上手快、改拓扑不动代码，SFT/微调团队友好；但 plan 与模型强耦合（tp_plan 键写死层路径），换模型要重写整套 YAML，且开关组合的合法性只能靠文档约定。

优文档级 chunk/ZigZag 均衡让 1M 长序列训练成为现实；SWA 窗口前缀交换进一步压 CP 域通信量

优KV-AllGather 路线快速工程化：TND CP + halo 交换后通信开销大幅下降，还带 vision-CP；与 1M 分块计划配合后已具备长训能力

缺仍限纯文本/图文部分场景，融合开关组合约束多
长序列 1M（seq 1048576 + CP128 脚本）；RoPE 运行时按训练长度建表 1M（11-16 合入 DSV41_1M_seq Adapt）：BSND CP + enable_long_sequence_chunking 分块计划——FP32 索引流式分块合并 top-k、attention 分 tile 重算、共享专家与融合 mHC premix 分块、cp_chunk_loss 复用

优1M 能力是稀缺卖点：长文档/代码语料 CPT 无需截断，RoPE 按训练长度建表避免位置外推误差

优1M 用「分块计划」而非只靠 CP：索引流式合并 top-k 避免全量 score 物化，与 CP 正交叠加；速度上限取决于分块粒度调参

缺分块计划参数多（索引阈值/tile 尺寸），调优成本高；默认关闭，需要显式启用
torch.compile 支持：每 TransformerBlock 整图（aot_eager / inductor）；负载均衡路由保持整图（含 MoE 通信），数据依赖路由对 dispatcher graph-break；11 月修复 CP 训练下的 compile 报错与挂起（fe968804）、保留 FSDP RS overlap（b780d3ae）、DeepEP GraphTrainer 支持 full Inductor overlap 不支持（融合路径仅 eager autograd 一阶梯度）；Engram Host 表路径遇 compile 会显式拒绝（防表未更新的静默错误）

优整图入图 + AutoFuse 算子自动融合是吞吐的关键杠杆，CP/DeepEP 场景的 compile 问题也已修复，全 Inductor 下还能保住 RS overlap

缺编译图按 MoE 路由形态二分：数据依赖路由（真实训练常态）时 MoE 通信在图外，实际加速比依赖路由形态

缺eager-only 意味着逐 kernel 启动开销无法用编译消除，吞吐上限受 launch overhead 限制；Host Engram 与 compile 的冲突被显式拒绝而非支持

NPU 算子机制operator dispatch

torchtitan-npu：配置层替换
  • @override(target=…Config, exact=True) 注册工厂，启用后模块类整体被换掉（如 AscV41SparseAttention 替换参考 CSA2）。
  • kernel geometry 是 override 的 kwargs 而非 config 字段；底层封装在 ops/ascendc/（compressor、mhc、grouped_mm、MoE permute/unpermute）。
  • 备选后端：TileLang（mHC pre/post，单卡验证）；arch22 TND 的 A3KeyWorkaround；torch.compile + Inductor AutoFuse 算子自动融合。
FSDPTurbo：算子层分发
  • register_op(op_name, device_type) 字典注册 + dispatch_op 按当前 accelerator 分发，缺 NPU 实现回退 CPU；语义层 ops/*.py → npu/cpu/cuda/triton 后端。
  • 按型号自动选实现：A3/910B/910C 用 LightningIndexerV2/SparseLightningIndexer；950DT 用 QuantLightningIndexer（MXFP4 打分打包，AOT profile 固定 index_topk=512，需 Python 3.11 + cannbotdsl）。
  • 模型内 device.type == "npu" 分支（RMSNorm、silu_mul）；Triton inplace_rope 来自 mindspeed_ops。
机制差异的本质：torchtitan-npu 把融合当成「模型形态的改变」（模块类被换、元数据契约共享，因此能编译入图）；FSDPTurbo 把融合当成「实现的可替换」（模块结构不动、算子分发，因此开关粒度更细、回退更容易，但难入图）。
训练影响：torchtitan-npu 的融合直接替换模型组件，吞吐收益完整（通信+计算+调度一起融合），但一个 override 出错会改变模型行为，必须靠双栈对照兜底；FSDPTurbo 的融合只换算子实现，出错面小、逐开关验证成本低，适合「融合渐进上线」，但每个算子各自为战，端到端加速比封顶。

方面torchtitan-npuFSDPTurbo影响与训练优缺

缺必须先跑一遍离线反量化得到 BF16 副本，准备链路多一步且容易版本错配

优化器optimizer

部分torchtitan-npuFSDPTurbo影响与训练优缺
主干参数 Muon 为主（NS steps=10、nesterov、match_rms_adamw，lr 1e-5）；FlexShard 逐头 BlockShard（wq_b/wo_a），每层按 attn/dense/routed 分 3 bucket 防 NS all-gather OOM；AdamW 为 fallback；A5 示例默认关闭 optimizer swap（753a3c07） AdamW + CosineAnnealingLR 默认；11 月引入 MuonAdamW（fsdp_turbo/optimizer/muon.py，基于 Keller Jordan/Moonshot 开源实现）；另有通用 AdamWSwap（CPU swap 优化器状态）特性

优Muon 在 MoE 大模型上的收敛效率优势已有公开证据，同等 token 预算下 loss 更低；逐头分 bucket 的 FlexShard 布局防住了 NS 正交化的大 all-gather OOM

缺Muon 超参（NS steps、lr 匹配函数）敏感且和 AdamW 调参习惯完全不同，用户迁移学习成本高；bucket 策略对拓扑变化敏感

优AdamW + cosine 是最低调参风险的默认组合；MuonAdamW 引入后两种优化器可选用，SFT 与预训练不再二选一

缺MuonAdamW 尚未见 V4.1 大规模训练的公开验证记录，收敛收益待确认
Engram 参数 HostSparseOptimizersContainer + SparseAdam（lr 5e-5）；跨 EP 拓扑的 checkpoint 恢复修复（1e1e60b） 自研 ActiveRowAdam：SparseAdam 等价更新限定在稀疏梯度命中的活跃行，规避原生 SparseAdam 的「BF16 权重 += FP32 稀疏」全表混合精度加；EngramOptimizer 编排 dense + sparse + 调度器容器

优挂在 torchtitan 的优化器容器体系上，与调度器/checkpoint/拓扑恢复复用同一套基础设施

缺原生 SparseAdam 的混合精度稀疏加成本随表大小增长（约 3.84 亿行时 CPU 更新是可感知的开销），需要靠 host 表实现层规避

优ActiveRowAdam 把每步更新严格限定在活跃行——CPU 优化器步的耗时与活跃行数而非表大小成正比，这是针对 98B×2 表的针对性设计，长训中每步都省

缺自研优化器要自己维护与 SparseAdam 的数值等价性证明和 checkpoint 兼容
状态交换 swap_optimizer（novaswap）：优化器状态驻 CPU swap buffer，DCP 零拷贝视图读写 Engram 权重与 moments 常驻 CPU pinned；未将主干优化器状态下沉 CPU

优优化器状态下沉 CPU 后，NPU 显存只装参数+梯度，同等卡上能开更大模型或更大 batch；DCP 零拷贝视图让 swap 态 checkpoint 读写不经过 GPU

缺swap 依赖 novaswap 组件与 PCIe 带宽，optimizer step 的隐含时延增加；checkpoint 恢复要求正确拓扑

优Engram 常驻 CPU 是唯一可行解（单表 183 GiB 放不进显存），实现上避免多余的显存↔主机搬运

MTP / DSpark未实现结构保留、训练禁止（V4 主线已加 MTP，V4.1 训练仍禁）

场景选型：我要训练什么，该选哪个？

按真实训练任务出发给出推荐。每个场景给出首选框架、并行/精度/优化器的具体配置要点，以及选择理由；两仓均以 2026-11-23 master/main 为准。

为什么：这个场景的胜负手是「单位 token 成本」——block-FP8 量化训练 + DeepEP 通信量化 + 整图 compile 入图三者叠加，只有 torchtitan-npu 同时具备；大 EP128 摊薄专家显存，1M CP 方案直接可用。FSDPTurbo 在此场景缺量化训练、缺 compile、EP dispatcher 默认保守，吞吐差距会被集群规模放大。代价：Muon 调参与 override 列表的学习成本，且依赖 torchao_npu/cann_ops 版本配套。

一页速查

决策原则

规模大、要吞吐极值、要量化/超长序列 → torchtitan-npu（场景 1/2/5/6/8）。 集群小、要迭代快、要 HF 生态与数值可预期 → FSDPTurbo（场景 3/7）。 图文 CPT 按数据形态选（场景 4）。两条路线共用同一 CANN 算子生态与 Engram 存储策略，核心差异不在「能不能训」，而在「为哪种工作流优化」：torchtitan-npu 为 recipe 化的大规模预训练优化（显式启用、可审计、性能优先），FSDPTurbo 为声明式的微调与研究优化（易上手、易回退、易对照）。若团队同时承担两类工作流，按场景分开选型比统一到一个框架更现实。

结论与借鉴

两者不是竞争关系，而是同一模型在两种框架哲学下的两次工程化，互有对方值得吸收的部分。

总判断（2026-11-23 更新）

结构层（组件、几何、融合算子来源、Engram 存储策略）两边高度同源；分化发生在框架耦合层——torchtitan-npu 用「配置级替换 + 显式启用」换取了 compile 入图和量化栈的完整性，代价是与 torchtitan 上游的强绑定；FSDPTurbo 用「vendored 参考 + 算子分发」换取了对官方实现的逐行可对照性和 HF 生态的低门槛接入。值得注意的趋势：11 月中下旬两边在快速收敛——FSDPTurbo 补齐 1M 长序列、attention 重计算、Muon、torchao 量化栈与 TND+融合压缩，torchtitan-npu 打通官方 MXFP8 整包读取并将 DeepEP 设为默认；两者的「独有卖点窗口期」正在缩短，长期差异将收敛到框架哲学本身（override 显式启用 vs plan 声明式配置）。

FSDPTurbo 可向 torchtitan-npu 借鉴

量化训练在 V4.1 上的实际接入（recipes + QAT + 量化注意力 backend 的「独立 backend + 同开契约」模式，当前 FSDPTurbo 已有 torchao 栈但 V4.1 未接）；官方 MXFP8 整包直读（省去离线反量化）；整图编译与 MoE 路由形态二分的经验；Muon FlexShard 逐头布局防 NS OOM 的工程细节。

torchtitan-npu 可向 FSDPTurbo 借鉴

ActiveRowAdam 活跃行优化器（比 SparseAdam 更省的 CPU 更新路径）；meta 设备延迟初始化的种子派生方案；长序列分块计划（enable_long_sequence_chunking 的流式索引合并 top-k，与 CP 正交）；TND/BSND 双布局对照工具链与在线打包；mock 数据生成器；attention recompute 的 replay 状态副本方案。

潜在的互操作风险

两边 Engram 表都按「全局逻辑行、2048 行对齐」保存，但 HF 键映射与量化格式处理各自独立（torchtitan-npu 现已支持读官方 MXFP8 整包，FSDPTurbo 要求已反量化 BF16）；若需跨框架迁移 checkpoint，Engram 与 experts 打包键（gate_up_proj/down_proj vs 上游 V3 布局）需要专门转换器。
