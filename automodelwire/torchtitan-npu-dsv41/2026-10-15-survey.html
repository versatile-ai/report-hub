1 · 定位

torchtitan 是什么:上游框架 + 昇腾扩展

两个名字是两层东西:torchtitan 是 PyTorch 官方的训练参考框架;torchtitan-npu 是华为 CANN 社区在它之上做的昇腾后端扩展插件——不是 fork,基线钉死、机制注入。

上游 · PYTORCH 官方

torchtitan

  • pytorch 组织开源的大规模模型训练参考框架,native PyTorch 单代码库,对照 Megatron-LM / NeMo 等重量级框架,定位是生产级训练架构的可读参考实现
  • 并行:FSDP2 · TP / CP / PP(4D 并行)· EP + DeepEP · async TP
  • 执行:torch.compile(Inductor / aot_eager)· Muon 优化器 · MTP
扩展 · 华为 CANN 社区 · BSD-3

torchtitan-npu(GitCode)

  • 非 fork:上游基线钉在 torchtitan v0.3.0,依赖 torch_npu 2.14.0.dev + CANN 9.x
  • 两层接入:override.imports 配置级组件替换 + PyTorch backend 注册补齐 NPU 后端缺口
  • NPU 能力:融合算子(AscendC / Triton / TileLang / PyPTO)· 显存(Swap / Virtual Optimizer、CPU offload)· 低精度(MXFP4 / MXFP8、block-FP8、HiFloat8、KV 低精度)· 维测(Profiling、内存快照、弹性恢复)
  • 支持模型:DeepSeek-V3.2 / V4 / V4.1 · Qwen3.5;README 自述性能(Ascend 950 图模式,DeepSeek-V4-Flash):MXFP8 单卡 2126 tokens/s @4k 序列,1M 序列 1325 tokens/s

3 · 修改点

DeepSeek V4.1 适配的五处修改点

适配不是单点补丁,而是四层结构:独立模型栈(①)、并行形态选择(②)、A3 / A5 硬件分档的融合算子栈(③)、一处关键修复(④)与训练配方及 checkpoint 路径(⑤)。①–④ 编号与图 1 一致。

  1. 1

    独立模型栈

    torchtitan_npu/models/deepseek_v4_1/ — attention.py · config_registry.py 等

    独立于 deepseek_v4 目录,不共享代码。CONFIG=deepseek_v4_1_flash 对齐 HF 官方结构:

    • 40 层 · hidden 5120 · 384 路由专家 + 1 共享专家 · top-6 · MoE 中间维 2304
    • attention 64 heads × 512 · Q/O LoRA 1280/1024 · ViT 32 层(图文多模态)
    • Engram 位于第 1 / 14 层,逻辑表行数 384,006,168 / 384,016,682
    • V4.1 特有结构:压缩稀疏注意力(CompressedSparseInnerAttention2)· lightning indexer · Engram 表

    边界:不支持 MTP(HF 额外 3 层)、DSpark、GraphTrainer;官方 FP8 / FP4 权重发布格式 ≠ 本入口的训练量化配方。

  2. 2

    并行形态

    examples/deepseek_v4_1/*.sh 并行参数 + 模型入口校验

    • FSDP2 + 专家并行 EP,TP / CP / PP = 1;spmd_types / full_dtensor 权重切分
    • 不支持的组合在入口直接拒绝(显式报错,不静默降级)
    • issue #152 命令即标准形态:单节点 16 卡,DP-shard 16 × EP 16,eager 模式(--compile.no-enable)
    • 多机:A3 每机 16 卡(EP128 / FSDP128);A5 每机 8 卡,默认开启 SMLA / LI 与 block-FP8 训练
  3. 3

    A3 / A5 硬件分档融合栈

    融合开关 override(脚本 CLI_OVERRIDES 通道)+ CANN .asc 融合算子

    维度A3A5
    节点形态每机 16 卡(16 die)· 单卡 64 GiB HBM每机 8 卡 · README 标注 Ascend 950 平台
    融合算子RMSNorm · 文本 RoPE asc_complex · 视觉 RoPE asc_half_rotation · MoE token dispatcher · mHC postA3 全部,文本 RoPE 换 asc_partial,追加 SwiGLUGroup · sparse_attn.asc · lightning_indexer.asc · mHC Sinkhorn
    默认量化不默认量化默认 SMLA / LI + block-FP8
    V4.1 稀疏注意力路径无融合算子 → 退回 attn-gym 0.0.9 reference 实现专用融合算子 sparse_attn.asc
    硬约束:A5 上 sparse_attn.asc 与 lightning_indexer.asc 必须同开。前者反向在 topk_scores 梯度上产出 indexer 教师(SMLAG),后者以此为教师更新 indexer(SLIKG),单开任一在模型构造时即抛 ValueError。
  4. 4

    A3 稀疏注意力 OOM 修复

    torchtitan_npu/models/deepseek_v4_1/attention.py(+127 / −14,PR #974)

    • reference 路径的 selected_attention 改为按 query 维分块:_selected_attention_tiled
    • 块大小由环境变量 TORCHTITAN_NPU_SPARSE_ATTN_CHUNK 控制,默认 512,非法值抛 ValueError
    • 机制、保真语义与修复前后对比见第 4 节
  5. 5

    训练配方与 checkpoint 三路加载

    examples/deepseek_v4_1/ — CPT / SFT / LoRA × 4k / 1M × A3 / A5(含 debug/ 8 卡变体)

    • checkpoint 三路:原生 DCP 断点续训 · HF 权重初始化 · Engram MXFP8 官方量化格式直载(V4.1 主线尚不能读取官方整包的非 Engram 量化权重,如 Attention)
    • 优化器 Muon(lr 1e-5)+ swap_optimizer;数据 CC12M 图文(默认仓内 32 条样本的 cc12m-test)
    • tokenizer 经 --hf-assets-path 注入,该参数不加载模型权重;初始权重另设 CKPT_INIT_LOAD_PATH
4 · 关键修复

PR #974:A3 稀疏注意力 OOM 的修复机制

A3 没有 V4.1 稀疏注意力的融合算子(那是 A5 专属),退回 reference 实现后,整条 fp32 张量链一次性物化,单层前向峰值 35–40 GiB,叠加常驻权重后超出单卡 64 GiB HBM——第一个 step 的 forward 即 OOM(EL0004,报错算子 aclnnInplaceCopy)。修复只改 attention.py 一处:按 query 维切块。

保真 · sink 列保留 保真 · 重复 index 的 log(counts) 加权 保真 · P@V bf16 量化 → fp32 累加 保真 · 不再计算被丢弃的 LSE

5 · 参考

对本项目的三点参考

  1. 训练引擎选型新增候选

    2026-09-18 调研时,NPU 侧 MindSpeed-LLM 尚无 V4.1 实现,NeMo Automodel 是唯一完整 V4.1 训练栈;torchtitan-npu 现已覆盖 DeepSeek V4.1-Flash 的 CPT / SFT / LoRA(含 1M 长序列与 Ascend 950 64 卡全参低精度复现),成为 NPU 原生的完整 V4.1 训练栈。

  2. 分块稀疏注意力 = 无融合算子硬件的参考实现范式

    PR #974 用「query 维分块 + 逐位等价证明(max diff = 0)」同时解决显存与数值可信度,与本仓数值对拍门禁的参考臂方法论同构,可直接借鉴。

  3. Engram MXFP8 官方格式直载

    torchtitan-npu 已打通 Engram 部分 official MXFP8 量化权重的直载训练(非 Engram 部分如 Attention 尚不能整包读);与 models/DeepSeek-V4.1-Flash/ 交付物的量化路线决策直接相关,值得跟进其补齐进度。
