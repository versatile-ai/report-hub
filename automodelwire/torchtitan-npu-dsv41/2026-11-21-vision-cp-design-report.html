训练引擎适配 · 设计报告

让带视觉塔的模型也能切分长序列:
视觉栈接入上下文并行(Context Parallelism)的设计

2026-11-21 · 基于昇腾 910B 上的 torchtitan-npu 训练框架(torchtitan 的华为 NPU 适配层)· 只读分析 + 方案设计,尚未改代码

一页结论

问题:我们在 910B 集群上对一个带视觉塔的多模态大模型(DeepSeek-V4.1-Flash)做强化学习训练。长推理链要求几千 token 的序列,但显存不够:实测序列约 4900 token 时前向即溢出,目前只能收缩到约 2400 token 运行。上下文并行(把一条序列切到多张卡上算)是标准解法,但训练框架对带视觉塔的模型档位显式拒绝该并行方式。

判决:解禁可行,且改动面很小——深入源码后发现,序列切分与视觉前向在机制上天然解耦,冲突不在"布局"本身,而在三处显式守卫与一处记忆模块的语义缺口。方案合计改动 2 个文件、3 处,分两阶段落地,均附带可独立复跑的验证门。

为什么社区没先做:上游框架在三周内为纯文本栈建成了完整的上下文并行机制(12 个提交),但视觉路径零提交——门禁注释自述"视觉路径尚无上下文并行契约"。真正难的不是代码量,而是正确性契约的逐点证明(切分后所有与位置对齐的状态必须同步移动,错一处是静默的数值错误)。业界同形态先例 2026 年 10 月才在 Meta torchtitan 主线出现(Kimi K3 的多模态上下文并行),我们做的是把已验证的形态接到华为分叉的 V4.1 栈,不是发明新机制。

一、问题:显存墙,以及唯一可用的纵向切分轴被拒绝

1.1 训练形态与硬约束

被训练的模型是 DeepSeek-V4.1-Flash:一个文本主干(MoE,混合专家)+ 视觉塔(ViT,约 0.8B 参数)+ 对齐层的多模态模型。图像经视觉塔编码后,以最多 1024 个占位 token 的形式嵌入文本序列;每个占位 token 的位置上,由对齐层输出的视觉特征替换/注入词嵌入。训练任务是数学题的强化学习(GRPO),策略模型需要生成几千 token 的推理链,因此序列长度(题面 + 图像 token + 推理过程)决定训练质量上限。

硬件是 2 节点 16 卡 910B,每卡显存上限约 58 GiB。该模型栈在框架里只允许三种并行:数据并行(每卡一条完整序列)、专家并行(把不同专家分到不同卡)、上下文并行(把一条序列切到多卡)。张量并行与流水线并行被模型栈显式拒绝(框架断言 TP=1、PP=1)。序列维度的显存压力只有上下文并行一条出路。

1.2 显存墙的实测位置

带视觉塔的模型档位、单卡承担整条序列(CP=1)时:序列 4864 token 前向即显存溢出;收缩到 2432 token 并打开选择性重计算后可运行。而纯文本档位的对照线在同样硬件上早已用 CP=2(两卡合算一条序列)跑通 4K 序列档——同代硬件上,上下文并行机制本身已工程化落地(上游有完整精度/吞吐对照表),不是纸面能力。也就是说:缺口不在"能不能切序列",而在"带视觉塔时框架拒绝切"。

1.3 拒绝的确切形态

框架在模型配置层有一条开关式守卫:多模态档的 accepts_context_parallel = False。请求上下文并行度 >1 时,配置阶段直接抛出 NotImplementedError("DeepSeek V4.1 rejects context parallelism on the multimodal stack"),训练尚未开始即终止。守卫的注释原文说明了意图:"the vision path has no CP contract yet"(视觉路径尚无上下文并行契约)——即上游自己也把它标记为"待定义",而非"不可能"。

二、为什么社区至今没有支持(意图分析)

  1. 需求交集小,优先级靠后。上下文并行的主战场是超长文本(长文档、代码、长推理链),这些场景绝大多数是纯文本模型;多模态模型里图像 token 通常只有几百到一千,很少成为序列长度的瓶颈。两个需求(多模态 × 超长序列 × 分布式)同时命中的用户群很小,上游框架不会优先投入。
  2. 文本栈的机制是刚建成的,视觉是自然的下一步。时间线很说明问题:我们锁定的基线(2026-10-30)之后,上游三周内落地了 12 个上下文并行相关提交——统一元数据接缝、按文档分块的负载均衡、模块化改造、与图编译的兼容修复——全部投向纯文本栈;同期视觉目录(8 个文件)零提交、零字节改动。这不是"不支持",是"还没轮到"。
  3. 真正难的是定义契约,不是写代码。上下文并行的正确性契约是一句话:所有与序列位置对齐的状态,必须随切分以完全一致的方式移动。文本栈的建设者逐点审计了每个消费者(注意力、旋转位置编码、损失、MoE 路由)。视觉路径引入了新的序列对齐簿记(图像特征位置表、token 类型表)和一个跨层记忆模块,每处都要重新证明"与切分可交换"。而这类错误是静默的——张量形状全部对得上,数值却写错行(上游自己的测试注释记录过:分片派发下整片写回会写进错的那一片,loss 只在小数点后第三位漂移)。面对静默错误,工程上的正确选择就是硬门禁:宁可拒绝,不放半支持。
  4. 业界先例刚刚出现,形态已被验证。Meta torchtitan 主线 2026-10-06 合并了第一个多模态上下文并行支持(Kimi K3):做法是"与 token 对齐的视觉索引随 token 一起切分、视觉塔输出整行复制、每张卡只在本地做特征注入"。我们这次分析的结论是:V4.1 的视觉注入与它结构同构。因此本方案的性质是移植已验证形态,置信度来源不是我们的聪明,而是先例的存在 + 下面的机制推导。

三、难点的本质(从原理拆解)

3.1 这套上下文并行用的不是"连续截断",是"置换 + 均分"

V4.1 文本栈的切分布局叫按文档分块(doc-chunk):为了均衡注意力负载并保持逐文档的池化对齐,切分前先把整行 token 按"属于哪篇文档的第几块"稳定重排,再均分给各卡。第 r 张卡拿到的不是序列的第 r 段,而是每篇文档的第 r 块、按文档顺序排好的一串行。这意味着任何"按序列位置索引"的张量都必须经过同一个置换——这是问题的第一个棱面。

3.2 视觉注入是"绝对位置"语义

图像特征注入的实现是:拿一张 [序列长] 的位置表(每个 token 若是图像占位,则登记它在视觉特征库中的行号),用"找出所有登记位 → 按行号取特征 → 写回对应词嵌入"三步完成。切分发生在前向开始之前,注入发生在词嵌入之后——注入看到的是本卡局部行,位置表却还是整行的。若不同步置换位置表,轻则形状不匹配崩溃,重则特征写进别的 token(静默错误)。这是第二个棱面,也是最像"视觉与 CP 不兼容"的表象来源。

3.3 记忆模块的"行内前驱"问题

模型内置一个检索式 n-gram 记忆模块(代码名 Engram,按"当前 token 前若干个 token"做哈希查表)。在 doc-chunk 布局下,某行的"文档内前驱"不再是一段连续窗口(整行顺序下,前一窗口行可能是另一篇文档的尾巴),所以文本栈的解法是:切分之前按置换预先构造每行的前驱表,切分后各行自带前驱、零跨卡通信。图像给这一步加了新语义:文本的 n-gram 不允许跨过图像 token(避免把图像占位当普通词做哈希),而非并行路径已有一套"屏蔽图像前驱"的既有语义。并行 × 图像的组合,上游留了一个显式的 raise("上下文并行目前只支持纯文本输入"),因为前驱表构造点不知道图像位在哪。这是第三个棱面。

3.4 两个客观限制(方案必须绕开而非对抗)

  • 静默错误无法靠形状检查兜底 → 验证必须靠"小输入 + 手推期望值"的纯函数对拍,和同配置逐位对比,不能只看"跑起来了没崩"。
  • 本代硬件跨并行度无逐位可比性:910B 上不同并行度会命中不同的内核实现选择,上游文档明言跨度对比不保证逐位(差异可达 1e-1 量级,打开确定性档位后才有逐位结论,而该档位在 910B 上不存在)→ 验证判据必须锚定"同一并行度、改动前后逐位相同",跨并行度只做量级一致性。

四、方案:关键洞察是"解耦",不是"给视觉塔设计切分"

直觉方案是"把视觉塔也切了"——本方案明确不这么做。源码取证给出三个分离,把问题从"设计视觉栈的切分机制"降解为"让两张簿记表随行、补一处记忆语义":

  1. 视觉塔的输入是图像,不是 token 序列 → 视觉塔永远不需要参与序列切分。每张卡复制完整图像,塔输出一份完整的特征库;冗余计算,但语义零冲突(参数由数据并行的分片机制统一管理,梯度自动跨卡归约)。成本核算:约 0.8B 参数的前向 ×2,在 2 节点档远小于训练步时,不为它引入同步点。
  2. 注入是"位置集合"语义,与行排列顺序无关 → "找出所有登记位、按行号取特征、写回"这一操作,对整行做一次 = 对各卡局部做一遍再拼回(置换前后两侧同变换,内容不变)。这正是 Kimi K3 先例的机制内核。因此注入函数本身零改动。
  3. 真正必须随 token 移动的只有两张簿记表 → 把它们并进切分调用即可。框架的切分函数本来就是"对一个张量元组统一置换再均分",追加两个成员,它们自动获得与 token 完全一致的行序——零新布局代码。

随序列同置换、同均分(切分调用中的元组)

  • token id(输入)
  • 标签(监督信号)
  • 位置(文档内坐标)
  • token 类型表 ← 新并入(文本/图像协议标记)
  • 图像特征位置表 ← 新并入(占位 token → 特征行号)

整行复制、每卡一份(不进切分调用)

  • 图像 patch 张量(视觉塔输入)
  • 图像网格表(每图的宽高)
  • 视觉塔输出特征库(注入的数据源)
