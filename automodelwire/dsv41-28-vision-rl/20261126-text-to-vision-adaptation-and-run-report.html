DeepSeek-V4.1-Flash 文本层 → 视觉层适配：改动差异与 50 步全同步实验报告

对象：带视觉塔的 64 专家强化学习变体（28-vision-rl），四节点训练 + 四节点推理（DP4×TP8=EP32）

0. 阅读前提与结论先行

前提。本报告假设读者没有任何本会话上下文：所有内部代号在首次出现处给出可读定义，术语只用有公开定义的词（EP / CP / DP / pearson / KL / DCP 等）。文中“文本基线”指同模型不带视觉塔的纯文本强化学习变体（27-hsdp-reduced-expert-rl），“视觉变体”指本报告对象（28-vision-rl）。

一句话结论。视觉层适配在机制面全部打通——49 步完整训练每一步都把 8864 个权重键从训练侧导出并热更到推理服务，首步训推一致性 pearson 0.99912（门线 0.995）、HBM 32.7 GiB、Engram 冻结形态合法、零崩溃；但训练信号面失败——图文样本的原始奖励恒为 0，唯一梯度来自“响应超长惩罚”，策略在第 16 步前后塌缩到极短输出，此后优势恒零；末步（第 50 步）检查点额外触发 HF 分片导出，把头部节点内存打爆（OOM），本轮以 49/50 步结束。

1. 从文本到视觉：适配原理、改什么、为什么改

1.1 基线形态

文本基线是“减专家”路线：把 DeepSeek-V4.1-Flash 的 384 个路由专家裁到 64 个，用真实权重（非随机初始化）做 GRPO 强化学习，训练侧引擎为 torchtitan-npu、编排为 verl 主线，推理侧为独立部署的 vLLM 0.30 服务；权重不共享文件系统，而是每步由训练侧导出为分片文件、推理侧热加载。

1.2 视觉层要接进来的三件事

面文本基线的形态视觉变体必须变成什么
模型面模型只含语言塔 + MoE + Engram 记忆表视觉塔（ViT）与 aligner 进入训练图：新增约 306 个视觉权重键 + 32 个 aligner 键，且必须在 CP>1 的序列切分下正确参与
数据面纯文本数学题，prompt 里只有 token几何图文题（geo3k）：样本带 images 列与 <image> 占位符；rollout 必须以 base64 图像走多模态对话端点；奖励函数换成题目判等 + 格式分
同步面导出 8518 个文本权重键，热更后推理服务直接可用视觉键必须一起导出并热更；同时要有“键面守卫”防止静默退回纯文本形态；热更后还要复位推理侧的多模态编码缓存，否则下一步图文请求会命中失效缓存

1.3 三条不可让步的约束（决定了改动形态）

  • 真实权重红线：视觉塔与 aligner 必须是官方 BF16 权重，不得随机初始化——因此不能复用文本基线那套 8518 键的权重视图（它没有视觉键），必须自建 64 专家 + Engram + 视觉的权重视图。
  • 训推同源：训练侧看到的视觉表示与推理侧必须来自同一份权重、同一套预处理，否则一致性指标没有意义。这直接催生了“视觉特征/中间量落盘”的取证仪器。
  • 不改框架、不 monkey-patch：所有对 verl / torchtitan-npu / vllm-ascend 的修改只能以补丁（patch）形式存在，附单元测试与锚点；模型侧只能通过框架公开扩展点接入。

2. 改动点逐条展开

下表按“面”组织。每条给出：动机（为什么非改不可）与验证方式。补丁编号是仓库内补丁文件的顺序号，括号内为补丁文件行数。

2.1 模型面

① 视觉栈在 CP>1 下解禁（0033-ttnpu-vision-cp-l0.patch，123 行）

为什么。训练侧用上下文并行（CP=2）把一条长序列切成两段分给两个 rank。视觉 token 进入序列后，切分点会把图像占位符切开；原实现对“视觉 + CP>1”直接 raise。改什么。把视觉序列键纳入切分与逆置换、补形状防御断言、删除强退分支。验证。overlay/tests/test_vision_cp.py + 图文三步轮 pearson 0.9985–0.9989。

② EP 梯度裁剪按 mesh 分组（0041-torchtitan-ep-clip-mesh-group.patch，101 行）

为什么。视觉参数没有被并行标注覆盖，FSDP 用扁平网格包装，而文本参数用二维网格；梯度裁剪时把两组张量 stack 到一起会崩 “all operands must have the same mesh”。改什么。按 mesh 分组各自求范数再合并。验证。视觉 + CP=2 三步训练不再崩。

③ 模型 flavor 分流与视觉视图（0001/0002 补丁 + 自建权重视图）

为什么。训练侧要构造带视觉塔的模型，推理侧同一份权重却必须过 vLLM 的配置校验（架构名必须是因果语言模型）。改什么。训练视图的架构名带 vision 字样触发 flavor 分流；推理视图保留同名权重但架构名改为 ForCausalLM，两侧都带 vision_config。

2.2 数据面

④ 多模态 processor 接入（dsv41_processor.py 新增 + 0034 白名单补丁，36 行）

为什么。verl 的处理器白名单里没有 V4.1 的多模态分支，图文样本到不了模型。改什么。新增处理器实现并把白名单补齐，产出 pixel_values 与图像占位符对齐。验证。test_dsv41_processor.py。

⑤ 模态键经 seam 注入（0035-verl-mm-seam-mmkeys.patch，111 行）

为什么。引擎桥在模型 forward 需要 attention_metadata 时会提前 return，导致“把多模态输入合并进 extra_inputs”那行永不执行——actor 收不到任何图像键，表现为“图文训推一致但视觉从未生效”。改什么。在提前 return 之前先注入模态键，并处理 CP>1 切分与设备归一。验证。test_r2_mm_seam.py + 日志中图像行 32/32 走多模态端点。

⑥ geo3k 数据池与原生奖励（geo3k_reward_native.py、third_party/mathruler、pylatexenc）

为什么。要与开源基线对齐，奖励口径必须是 verl 上游 utils/reward_score/geo3k.py 的原义（0.9×判等 + 0.1×格式）。改什么。以签名适配器逐字转调上游函数，并把其依赖的 mathruler / pylatexenc 逐字随 overlay 分发，避免镜像内版本差异。验证。数据池 md5 钉值（train 2101 行 / test 601 行）。

2.3 同步面

⑦ 视觉键门控与键面守卫（dsv41_npy_writer.py，+79/−4）

为什么。导出白名单原先按“延迟键族”排除视觉键，视觉塔会静默不同步；而一旦视觉键缺失，训练与推理的视觉表示立即分叉。改什么。把视觉键族改为由 VISION_TOWER 环境变量门控；在收尾校验里加“视觉键面 ≥300”的硬门，缺键即失败而不是静默降级。

⑧ 专家栈 eid 由 placement 直接解算（v3_npy_dump_engine.py，+126）

为什么。四节点形态下 64 个专家被 32 个 rank 切分，每 rank 只持 2 个非连续槽位；原实现按“每 rank 连续一段”假设，导致同一批专家被两个 rank 重复写、另 32 个无人写。改什么。不再手推映射公式，改为用与真实权重逐字相同的 (device_mesh, placements) 分发一个 arange，取 .to_local() 作为本 rank 的全局索引；并新增全局划分校验（各 rank 索引汇总必须恰好铺满 0…63）。验证。test_v3_npy_dump_engine_eids.py（含事故数据必判 FAIL 的反证）。

⑨ 切分宽度实测替代 ep×cp 乘法（同上，v3_npy_dump_engine.py）

为什么。写端校验用的“每 rank 应写多少专家”由配置里的 EP 值乘 CP 推出，但专家张量实际切分份数由 dp_shard 与 CP 共同决定，二者不是一回事。改什么。改为实测：全局槽数 ÷ 本 rank 本地行数。

⑩ 热更后复位多模态编码缓存（dsv41_npy_writer.py 新增函数 + 0032 类补丁）

为什么。worker 侧重载只清了自己的编码器缓存，调度器侧的缓存管理器不知道；同一张图（geo3k 图片在多个 prompt 间复用）下一步会被判“已缓存”，worker 查不到 → 抛 Encoder cache miss → 推理服务整机退出。改什么。热更成功后调用推理服务官方的两个 dev 端点 /reset_encoder_cache 与 /reset_mm_cache（视觉档严格、纯文本档宽容）。验证。test_v3_serve_mm_cache_reset.py + 50 步轮全程未再复现。

2.4 观测与发射面

⑪ 一致性取证仪器（0036 / 0037 / 0038 / 0039）

  • 0036：逐 token logprob 落盘，提供不依赖推理服务的判决量。
  • 0037：temperature=0 的 logprob 守卫——贪心解码下 logits/0 产生 NaN，会同时污染 pearson、梯度与熵。
  • 0038 / 0039：训练侧视觉特征与视觉塔中间量（patch_embed / norm）落盘，用于与参考实现逐层对账。

⑫ 发射与判读（engine-28.sh、config.env、judge-grpo.py）

新增 engine-28.sh 五段引擎（含视觉视图三连门：config 含 vision_config / 视觉键数 ≥300 / 架构名回显），场景配置新增 VISION_TOWER、V2_R2_IMAGE、图像行端点分流等开关；判读器按发射面环境变量推导并行期望值，避免回落到硬编码期望造成的误判。

  • Engram 合法形态：forward_only，层禁用 0，更新/导出/增量全 0。
